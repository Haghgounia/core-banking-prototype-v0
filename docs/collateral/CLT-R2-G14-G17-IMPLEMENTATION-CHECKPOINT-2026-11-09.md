## ۲. گام جدید — چه چیزی واقعاً کدنویسی شد

1. کنترل فیزیکی طرح شماره انتظامی V1.42 بدون صدور عدد: طول کد نوع از `CLT.COLLATERAL_TYPE.COLLATERAL_TYPE_CODE`، طول شماره مشتری **از `CifService.readiness().customerNo()`** و نه از شناسه فنی Party؛ ۴ رقم سال شمسی + ۳ رقم توالی + ۱ رقم کنترل؛ محاسبه طول بر پایه رشته بدون `double`/`long`.
2. بررسی **زنده Data Dictionary** ستون `CLT.COLLATERAL.COLLATERAL_NUMBER` و رد مغایرت با `NUMBER(19,0)`؛ کنترل طول بیشتر از ۱۹، غیراعدادی‌بودن و از دست‌رفتن صفر پیشرو در نوع NUMBER.
3. پیش‌بررسی **نامزد دارایی قبل از ذخیره Draft** با مقایسه فقط Stage در Oracle، با عدم افشای Party/Branch سایر مالکان؛ هیچ تضمین هویت پایدار یا عدم وجود دارایی فعال صادر نمی‌شود.
4. گزارش هر دو ارزیابی در **همان API موجود** `POST /api/v1/collaterals/introduction-drafts/registration-preflight` و نمایش در فرم معرفی؛ بدون API احراز هویت جدید یا DataSource جدا.
5. No final registration, no numbering sequence reservation, no DML on `CLT.COLLATERAL` and no automatic Oracle migration.

### تصمیم‌های لازم برای G-17 (نه فرضیات اجرایی)

- آیا شماره نهایی باید **عدد صرفاً ۱۹ رقمی** در Oracle بماند یا ستون رشته‌ای canonical اضافه/جایگزین شود؟
- طول و قالب واقعی `COLLATERAL_TYPE_CODE` و `CIF.customerNo` برای همه انواع/مشتریان چیست؟
- نحوه توالی یکتا بین سال/نوع/مشتری، سیاست دوره‌ای و رفتار بعد از ۹۹۹ شماره چگونه است؟
- رقم کنترل Luhn نمونه V1.42 و قالب ۴رقمی سال شمسی باید به تصویب مالک کسب‌وکار برسند.
- منبع Asset Identity قطعی برای هر نوع دارایی و سیاست Re-introduction چیست؟
