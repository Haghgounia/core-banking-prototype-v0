# CLT-R6H — یکپارچه‌سازی راه‌اندازی محلی بدون ورود شعبه

**نسخه:** 2026-11-04 | **مرجع ثابت:** CLT-ROADMAP-R1.0 | **پروژه:** Core Banking Prototype 0.11.0

## علت و تصمیم

گزارش‌های R6G و R6G-HF1 نشان می‌دهد Build/اجرای Spring آغاز شده، اما در ایجاد `collateralReferenceReaderPool` خطای `CLT_REFERENCE_READ_CONFIG_DENIED` رخ داده است. با وجود پیام موفقیت قبلی، در گزارش دوم اثر مشخصی از نصب HF1 و مقدار پیکربندی در JAR ثبت نشده است. به همین علت، R6H افزون بر اصلاح کد، **اثبات وجود کلاس اصلاح‌شده داخل JAR** و آزمون خودکار راه‌اندازی واقعی را الزامی می‌کند.

**هیچ توسعه‌ای در IAM انجام نمی‌شود.** R6H صرفاً DEV تک‌ماشینی است؛ در اجرای عادی، گیت JWT و حساب SELECT-only مستقل تغییری نمی‌کنند.

## تغییرات

1. هیچ کد شعبه‌ای از کاربر در نصب/اجرا درخواست نمی‌شود.
2. Backend با SELECT ثابت `SELECT MIN(BRANCH_CODE) FROM CLT.COLLATERAL WHERE BRANCH_CODE IS NOT NULL` اولین شعبه موجود را تنها یک‌بار و **در نخستین GET مجاز** تعیین و کش می‌کند. این انتخاب صرفاً برای حفظ قرارداد فعلی شعبه است؛ فیلتر اختیاری شعبه در UI هنوز بخشی از پوشش نهایی UAT نیست. از Query String، Header و Bearer Token برای تعیین شعبه استفاده نمی‌شود.
3. در نبود ردیف CLT، از مقدار غیرواقعی `CLT_NO_DATA` استفاده می‌شود؛ اطلاعات شعب دیگر بدون فیلتر ارائه نمی‌شود. اگر Oracle در دسترس نباشد، پاسخ 503 داده می‌شود؛ سرور نباید به‌دلیل Oracle Startup Crash متوقف شود.
4. اجرای محلی فقط با فعال‌سازی صریح، گوش‌دادن روی `127.0.0.1:8091` و HTTP GET مشخص در whitelist مجاز است. تمام گیت‌های Write/Financial خاموش باقی می‌مانند.
5. برنامه نصب کامل، Build و سپس بررسی واقعی کلاس Java در JAR و Health و ۴ GET اصلی R6D را انجام می‌دهد؛ **Build PASS بدون Runtime PASS پذیرش محسوب نمی‌شود.**
6. حتی در حالت محلی، DataSource موجود Prototype ذاتاً Oracle SELECT-only نیست. **این حالت فقط روی داده ساختگی و غیرمحرمانه و رایانه اختصاصی توسعه مجاز است.**

## نصب واحد

Backend قبلی روی پورت 8091 را متوقف کنید. سپس بسته R6H را Extract کرده و از پوشه خودش دستور زیر را اجرا کنید:

```cmd
INSTALL-BUILD-AND-RUN.cmd "D:\Projects\core-banking-prototype-v0"
```

خروجی مورد انتظار:
- `CLT_R6H_INSTALL_BUILD_PASS` پس از Build واقعی؛
- `CLT_R6H_JAR_ATTESTATION_PASS` پس از تطبیق bytecode؛
- `CLT_R6H_STARTUP_PASS` پس از Health HTTP 200؛
- چهار خط `CLT_R6H_R6D_*` برای وضعیت APIها. در صورت HTTP غیر 200، همان کد صریحاً گزارش می‌شود و UAT تأیید نمی‌شود.

**توجه:** وضعیت `CLT_R6H_UAT=NOT_APPROVED` تا اجرای دستی سناریوهای کارکردی در رابط کاربری ثابت است. تغییرات R6H توسعه R1 تا R5 را تأیید نمی‌کنند.
