# CLT R6D — تکمیل کنترل‌های رفتاری رابط و عیب‌یابی فقط‌خواندنی

**مرجع:** CLT-ROADMAP-R1.0؛ Core Banking Prototype 0.11.0؛ ارتقا از R6C.

## مسئله کشف‌شده در بازبینی سورس R6C

1. اگر هنگام دریافت پاسخ، کاربر فرم را ببندد یا Route/بخش را تغییر دهد، مقدار `requestSequence` لزوماً در همه مسیرها تغییر نمی‌کرد؛ پاسخ دیرهنگام می‌توانست انتخاب قبلی را بازگرداند یا وضعیت `busy` را ناهماهنگ بگذارد.
2. تغییر `section` در Query String همان Route به علت خواندن صرف `snapshot` الزاماً به بخش بازشده منتقل نمی‌شد.
3. رابط فهرست به صحت شکل `COLLATERAL_ID`، `COLLATERAL_NUMBER`، منبع شعبه، صفحه‌بندی و تطبیق شناسنامه با شناسه درخواست‌شده در زمان Runtime اعتبارسنجی اضافه نداشت.
4. تحلیلگر بدون لاگ فنی قادر نبود فقدان احراز هویت، غیرفعال بودن خواندن CLT، وجود نداشتن Route و مغایرت پاسخ HTTP 200 را از هم تفکیک کند.

## محدوده اصلاح

- سازگارکردن `busy` و `requestSequence` با بستن جزئیات، تغییر شماره انتظامی، بازنشانی Mode و انتخاب نوع نامعتبر؛ پاسخ قدیمی اجازه بازکردن خودکار جزئیات را ندارد.
- واکنش به `ActivatedRoute.queryParamMap`، بدون استفاده از Route یا منوی جدید.
- اعتبارسنجی ساختار داده و دقت `NUMBER(19)` با **رشته**. در پاسخ نامعتبر، رابط هیچ داده‌ای را انتخاب نمی‌کند و پیام مغایرت قرارداد نمایش می‌دهد.
- اضافه کردن پنل «عیب‌یابی یک‌کلیکی ارتباطات خواندنی» در میزکار R6A/R6C؛ چهار درخواست GET، با مهلت ۸ ثانیه، تنها با مجوزهای عادی همان نشست.
- امکان خروجی JSON از نتیجه چهار آزمون؛ فقط `key/state/httpStatus` صادر می‌شود. بدنه پاسخ، اطلاعات شعبه، شناسه، توکن و شماره‌های تجاری در خروجی وجود ندارند.

## قرارداد آزمون‌های فقط‌خواندنی

| شناسه | Endpoint | کنترل پاسخ ۲۰۰ |
|---|---|---|
| registry-readiness | `GET /api/v1/collaterals/readiness` | `registryReadEnabled=true` و وضعیت امنیتی مشخص |
| registry-page | `GET /api/v1/collaterals?page=0&size=1` | منبع `ORACLE_CLT_OWN_BRANCH` و ساختار صفحه |
| report-overview | `GET /api/v1/collaterals/reports/overview` | `ORACLE_CLT_READ_ONLY`، محدود به JWT branch، بدون مجوز تخصیص |
| reference-summary | `GET /api/v1/collaterals/reports/reference-summary` | `ORACLE_CLT_REFERENCE`، بدون گواهی ستادی |

**طبقه‌بندی:** `PASS`، `BLOCKED_AUTH`، `READ_DISABLED`، `MISSING_ROUTE`، `UNAVAILABLE`، `SERVER_ERROR`، `TIMEOUT`، `CONTRACT_DRIFT`.

- HTTP 401/403 نشانه **رد دسترسی توسط سرور** است؛ نباید به خطای ظاهری یا فقدان داده تقلیل یابد.
- HTTP 503 نشانه عدم آمادگی/دسترس‌پذیری خواندن CLT یا وابستگی‌های آن است؛ منبع دقیق را صرفاً از این کد نمی‌توان تعیین کرد.
- HTTP 200 فقط در صورت سازگاری ساختار پاسخ به `PASS` تبدیل می‌شود؛ این PASS هرگز **UAT PASS یا مجوز تخصیص/آزادسازی** نیست.
- این ابزار هیچ درخواست POST/PUT/PATCH/DELETE و هیچ درخواست اعتبارسنجی کاربر با دورزدن کنترل‌های امنیتی انجام نمی‌دهد.
- چهار فراخوانی صرفاً با کلیک تحلیلگر اجرا می‌شوند؛ بارگذاری صفحه باعث تماس خودکار نمی‌شود.

## آزمون تحویل

- نصب و Precheck روی سورس نسخه R6C؛ SHA-256، توقف در تعارض و نصب مجدد بدون تغییر.
- آزمون مستقیم قواعد خالص TS در `tools/clt/r6d/policy-smoke.cjs`؛ کنترل‌ها شامل امنیت و شکل خروجی JSON هستند.
- Build کامل Angular/Java فقط با دستور اجرایی روی Windows کاربر قابل ادعا است؛ وجود کد و آزمون خالص به معنی پذیرش مرورگر نیست.

## حدود اجرایی و موانع باقیمانده

- **هیچ تغییری** در IAM، CIF، DPS2، مسیرها/منوهای مشترک، Backend، DDL یا DML Oracle ایجاد نمی‌شود.
- خواندن CLT اگر در سرور خاموش باشد یا نشست معتبر نداشته باشد، همچنان 401/403/503 می‌دهد و نتیجه باید BLOCKED ثبت شود.
- عملیات ثبت قطعی، تخصیص مالی، رفع تخصیص و آزادسازی واقعی فعال نشده‌اند.
- R6 با آزمون واقعی مرورگر و ۱۰ سناریوی تحلیلگر خاتمه می‌یابد؛ R7 نیز به اثبات Oracle، تراکنش، Audit و قفل واقعی نیاز دارد.

## سناریوهای پذیرش مرورگر برای R6D

1. `collateral/registry` را باز کنید و هنگام بارگذاری فیلتر را تغییر دهید؛ پاسخ قدیمی نباید نتیجه جدید را جایگزین کند.
2. برای شناسنامه انتخابی بخش بیمه را باز و سپس صفحه را ببندید؛ پاسخ دیرهنگام نباید جزئیات را دوباره باز کند.
3. با URL `/collateral/lookup?section=valuation` وارد شوید؛ پس از جست‌وجو بخش ارزیابی باید انتخاب شود.
4. در همان صفحه Query `section=insurance` را بدون بارگذاری کامل تغییر دهید؛ عنوان انتخاب‌شده باید به‌روزرسانی شود.
5. در میزکار UAT روی «اجرای کنترل خواندنی» کلیک کنید. بدون مجوز، BLOCKED/503 نمایش داده شود و داده ساختگی ساخته نشود.
6. فایل JSON عیب‌یابی را صادر کنید؛ نباید بدنه پاسخ یا اطلاعات مشتری/شعبه/توکن در آن وجود داشته باشد.
