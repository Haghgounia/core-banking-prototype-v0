# CLT-RF1 — زیرساخت یکپارچه خواندن ۱۷ جدول مرجع و تحویل UAT بیمه‌گران

**مبنای سورس:** `core-banking-prototype-v0-2026-11-07-1652.zip` / `VERSION=0.11.0`، با ادغام UI بسته R3C شرکت‌های بیمه.  
**وضعیت:** Source/Static QA کامل؛ Runtime Oracle و UAT تحلیلگر تا اجرای محیط واقعی **تأیید نشده**.  
**دامنه:** R1 (Reference Data Integration) با پشتیبانی UAT دامنه R3 (Insurance). **نام و ترتیب R0–R7 بدون تغییر**.

## مسئله

در نسخه قبلی، R6K صرفاً `GET /api/v1/collaterals/groups` و `.../types` را در محیط ویندوز بررسی می‌کرد. این دو مسیر از **Registry Read Contract** و نه قرارداد عمومی ۱۷ جدول مرجع عبور می‌کنند. بنابراین نمایش صحیح ۲۸ گروه، اثبات دسترسی `GET /api/v1/collateral/reference/INSURANCE_COMPANY` نبود. متن خطای مرورگر هم کد واقعی HTTP را پنهان می‌کرد. نتیجه: یک صفحه می‌توانست با `HTTP 403` شکست بخورد، با وجود اینکه Build و Smoke Test قبلی موفق بودند.

این نسخه ادعا نمی‌کند که علت 403 در محیط کاربر صرفاً کَش یا Security است: بدون پاسخ HTTP و رکورد سرور نمی‌توان بین حالت راه‌اندازی، مجوز، تنظیمات و وضعیت دیتابیس حکم قطعی داد. برای همین آزمون **۱۷ قرارداد واقعی** اضافه شده است.

## مسیرهای فنی

- `GET /api/v1/collateral/reference/uat-matrix`: **فقط** وقتی `CLT_LOCAL_UAT_READONLY_ENABLED=true` است ثبت می‌شود. درخواست همچنان از همان `SecurityFilterChain` مخصوص `/api/v1/collateral/**` با `SCOPE_clt.reference.read` و محدودیت Loopback عبور می‌کند. در محیط غیرمحلی Endpoint وجود ندارد؛ در حالت لوکال POST/PUT/PATCH/DELETE باز نمی‌شود.
- در `CollateralReferenceRepository.readinessMatrix()` برای تمام ۱۷ نام ثابت Allowlist، `SELECT COUNT(*)` به‌همراه `SELECT` از کل ستون‌های تعریف‌شده با سقف یک رکورد اجرا می‌شود. جدول با **صفر رکورد** `READABLE` است؛ جداول با مجوز یا ساختار نامعتبر `UNAVAILABLE` می‌شوند؛ متن Oracle به کلاینت ارسال نمی‌شود.
- برای هر جدول همان Endpoint واقعی `GET /api/v1/collateral/reference/{table}?page=0&size=1` به‌وسیله `tools/clt/rf1/verify-rf1-runtime.cjs` فراخوانی می‌شود؛ HTTP و تطابق تعداد ردیف با Probe ثبت می‌شود. کلاینت فقط GET می‌فرستد و پاسخی را شبیه‌سازی نمی‌کند.
- در صفحه `/#/collateral/reference-data`، وضعیت ۱۷ جدول به‌صورت جدول تشخیصی نشان داده می‌شود؛ بدون تبدیل خطا به «صفر رکورد». در صفحات داده واقعی، 401/403/503 صریح‌تر گزارش می‌شوند و درخواست‌ها Cache Busting دارند.
- صفحه `INSURANCE_COMPANY` و لینک منو از بسته R3C روی آخرین کد ادغام شده‌اند؛ کدهای `TMP-INS-1403-*` تنها نامزد هستند، مجوز یا وضعیت ACTIVE نمی‌گیرند. پنل بیمه‌نامه همچنان **فقط بیمه‌گران ACTIVE** را فهرست می‌کند.

## معیار پذیرش یکپارچگی

`CLT_RF1_REFERENCE_READ_GATE_PASS; ALL_TABLES=17` و گزارش JSON با ۱۷ جدول `READABLE`، HTTP 200 و قرارداد page/size معتبر. تعداد بیمه‌گران صرفاً **واقعیت همان نشست Oracle** است و صفر رکورد نباید با خطای شبکه یا 403 اشتباه گرفته شود.

## سناریوهای UAT تحلیلگر

۱. در «مدیریت وثایق → اطلاعات پایه وثایق»، وضعیت ۱۷ جدول در ماتریس دیده شود.  
۲. صفحه «شرکت‌های بیمه (مرجع)» باز شده و اطلاعات واقعی نمایش داده شود. اگر ۴۲ رکورد COMMIT شده‌اند، ۴۲ ردیف در ۳ صفحه ۲۰/۲۰/۲ مورد انتظار است.  
۳. جست‌وجوی «بیمه ایران»، کد موقت، پاک‌سازی، جزئیات Modal، Escape، حفظ فوکوس/موقعیت بررسی شود.  
۴. تمامی شرکت‌های نامزد غیرفعال بمانند و در انتخابگر عملیاتی بیمه‌نامه ظاهر نشوند.  
۵. سایر جداول ممکن است صفر ردیف داشته باشند، اما UI باید خالی‌بودن را از 403/503 تفکیک کند.

## ممنوعیت‌های صریح

- هیچ Oracle DDL، DML، Seed، COMMIT یا تغییر `STATUS` توسط بسته اجرا نمی‌شود.
- هیچ کد IAM، احراز هویت سراسری، تنظیمات تولید، Scope غیرمحلی و Client-supplied branch اصلاح/توسعه داده نشده است.
- این نسخه **CRUD کامل عملیاتی** و عملیات ثبت بیمه‌نامه، ارزیابی یا تخصیص را فعال نمی‌کند؛ فقط زیرساخت GET را برای ۱۷ مرجع محک می‌زند.
- تغییر کد موقت، احراز مجوز بیمه مرکزی، تفکیک شرکت‌های مستقیم/زندگی/اتکایی، تصویب سیاست‌ها و فعال‌سازی همچنان گیت‌های داده/کسب‌وکارند.
