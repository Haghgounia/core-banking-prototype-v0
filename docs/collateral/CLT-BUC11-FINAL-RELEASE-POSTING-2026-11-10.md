# BUC-11 | پیاده‌سازی مسیر ثبت نهایی آزادسازی وثیقه (2026-11-10)

**مبنای سورس:** بسته BUC14/16 مورخ ۱۰ نوامبر ۲۰۲۶ (VERSION=0.11.0). **نقشه راه:** R5 بدون تغییر نام/تعریف. **مرجع کسب‌وکار:** BUC-11/SUC-14/BR-14 و R5C.

## اثر کسب‌وکاری پیاده‌سازی‌شده

مسیر مستقل از پیش‌بررسی قدیمی با APIهای `GET /api/v1/collaterals/{id}/final-release/posting-readiness`، `GET .../approved-permits` و `POST .../commit`، و دکمه مشروط در صفحه «آزادسازی نهایی» اضافه شد. `commit` پس از تأیید مستقل مبتنی بر Permit بانکی، **واقعاً وضعیت `CLT.COLLATERAL` را تغییر می‌دهد** و در همان تراکنش، رویداد جدید `CLT.COLLATERAL_STATUS_HISTORY` با لینک به رویداد قبلی درج و Permit مصرف می‌شود. شماره انتظامی، سوابق قبلی و ردیف‌های تخصیص بدون تغییر می‌مانند. مجوز مصرف‌شده با همان Actor و UUID قابلیت بازیابی Receipt تکراری دارد؛ UUID متفاوت یا تغییر نسخه رد می‌شود.

## کنترل‌های اجباری

- `COLLATERAL` و Permit روی همان DataSource مشترک با `FOR UPDATE` قفل می‌شوند؛ کنترل نسخه با CAS انجام می‌شود.
- Permit **از طریق هیچ API این بسته ایجاد یا تأیید نمی‌شود**؛ باید در فرآیند مستقل و مورد تأیید بانک صادر شده باشد. فیلدهای تأیید مستقل Maker/Checker، ارجاع حقوقی، تسویه تمام تعهدات، رفع تخصیص و موعد اعتبار در سمت Oracle کنترل می‌شوند. Poster نیز با هر دو شخص متفاوت است.
- `CLT.COLLATERAL_ALLOCATION` نباید تخصیص فعال، مقدار `USED` نامعتبر یا تخصیص در شعبه دیگر داشته باشد؛ تراکنش بدون وضعیت قطعی، زنجیره تاریخچه ناسازگار و وضعیت غیرمجاز نیز مانع‌اند.
- وضعیت مقصد از Config مصوب بانک خوانده و در `REF_COLLATERAL_STATUS` به‌صورت فعال، **غیرفعال از نظر استفاده و Terminal** بررسی می‌شود. صرفاً برچسب Terminal بدون نگاشت مصوب کافی نیست.
- `Idempotency-Key` UUID معتبر، `If-Match` قوی، scope بررسی و شعبه از Principal دریافت می‌شوند؛ در درخواست هیچ ادعای حقوقی/تسویه/مجوز بین‌شعبه‌ای از Browser پذیرفته نمی‌شود.
- **Prototype دارای principal محلی** و حالت UAT خواندنی، امکان ثبت نهایی مالی ندارند. این کنترل عمداً مستقل از UI است.

## گیت اجرای واقعی

- Config پیش‌فرض: `core-banking.collateral.final-release.posting-enabled=false`. دو مقدار `source-status-code` و `target-status-code` تا دریافت مصوبه بانک خالی‌اند. حتی روشن‌شدن Flag بدون Permit، Mapping و Schema تأییدشده عملیات را ممکن نمی‌کند.
- ساختار پیشنهادی `CLT.CLT_FINAL_RELEASE_PERMIT` **جزء ۲۶ جدول مصوب CLT نیست**. فایل `database/oracle/clt/releasepost/01_RELEASE_PERMIT_SCHEMA_CANDIDATE_NOT_APPROVED.sql` عمداً قبل از هر DDL با خطا متوقف می‌شود. اعمال ساختار باید جداگانه توسط DBA پس از تصویب صورت گیرد. نصب Patch هیچ DDL/DML اجرا نمی‌کند.
- **محدودیت مهم هم‌زمانی:** قفل سطر وثیقه تنها درصورتی مانع Race میان آزادسازی و ثبت تخصیص جدید می‌شود که *تمام* Writerهای تخصیص/وضعیت از همان پروتکل قفل Parent پیروی کنند؛ این پروتکل و اجرای دو Session Oracle هنوز تأیید نشده است. به همین دلیل مجوز فعال‌سازی تولیدی وجود ندارد.
- مجوز بانکی صرفاً با وجود متن ارجاع در Permit اثبات نمی‌شود؛ فرایند صادرکننده باید احراز، ممیزی و امنیت مستقل داشته باشد. Bank/DBA مسئول تأیید Permit Producer، توالی وقایع و وضعیت‌های مقصد است.

## وضعیت Use Case

| جزء BUC-11 | وضعیت |
|---|---|
| UI → API ثبت نهایی | کدنویسی‌شده |
| Oracle TX وضعیت + تاریخچه + Receipt | کدنویسی‌شده / فاقد اجرای زنده |
| کنترل شعبه، Actor، مجوز، Replay و Concurrency پایه | کدنویسی‌شده / آزمون قواعد مستقل |
| Schema مرجع Permit، صدور مستقل بانکی و Mapping وضعیت | نیازمند مصوبه و استقرار |
| فعال‌سازی و UAT Oracle/Business | انجام‌نشده؛ **BUC-11 هنوز پایان‌به‌پایان پذیرفته نشده** |

این گام توسعه‌ای BUC-11 به‌معنای حل G-09/G-13/G-20/G-21/G-22 یا تکمیل BUC-12 نیست. گام بعد از ثبت و تأیید واقعی BUC11، معرفی مجدد دارایی آزادشده با **شناسه دارایی پایدار، شماره انتظامی جدید و پیوند تاریخچه قبلی** است.
