# CLT-R3D — آزمون تحلیلی بیمه‌نامه بدون داده شناسنامه واقعی

**مرجع ثابت:** `CLT-ROADMAP-R1.0`، فاز **R3: ضامن، بیمه و ارزیابی**، `BUC-07`، `SUC-09`؛ مکمل UAT فاز R6، بدون تغییر نام/ترتیب R0–R7.

**مبنای توسعه:** آخرین ZIP کامل `core-banking-prototype-v0-2026-11-07-1652.zip` + تحویل موفق RF1 روی همان نسخه، `VERSION=0.11.0`.

## هدف

تحلیلگر بتواند پیش از آماده شدن `CLT.COLLATERAL_TYPE` و `CLT.COLLATERAL`، خود فرم بیمه‌نامه واقعی Angular را در میزکار UAT ببیند، فیلدها و کنترل شکلی را بررسی کند، گیت‌های داده را مشاهده و نتیجه را به JSON تبدیل کند؛ **بدون داده ساختگی، POST، DDL یا DML**.

## مسیر

`http://127.0.0.1:8091/#/collateral/uat` → تب **بیمه‌نامه وثیقه (R3)**. این تب همان کامپوننت `CollateralInsurancePanelComponent` را با `analystPreview=true` نشان می‌دهد. APIهای عملیاتیِ مبتنی بر شناسنامه در این حالت فراخوانی نمی‌شوند. یک فرم دوم جداگانه ساخته نشده است.

در پیش‌نمایش فقط سه درخواست GET از منابع واقعی خوانده می‌شود:

- `INSURANCE_COMPANY` برای آمار شرکت‌های نامزد و فعال؛ صفحه اول ۵۰ رکورد. تا وقتی همه رکوردها بارگیری نشده باشند، تعداد فعال **نامعلوم** است، نه صفر.
- `COLLATERAL_INSURANCE_TYPE` برای تعداد/وضعیت مرجع انواع پوشش.
- `COLLATERAL_TYPE` برای تعداد انواع فعال وثیقه، از Registry API موجود.

بر اساس آخرین شواهد محیط کاربر، ۴۲ شرکت نامزد غیرفعال/کد موقت، صفر نوع وثیقه، و صفر شناسنامه وجود داشته است؛ این اعداد هر بار از API خوانده می‌شوند و در UI هیچ عدد ثابتی به‌عنوان داده Oracle درج نشده است.

## دامنه قابل آزمون

| شماره | سناریو | نوع پذیرش |
|---|---|---|
| R3-INS-01 | کاتالوگ شرکت بیمه؛ فقط ACTIVE در فرم عملیاتی | خواندن Oracle / گیت داده |
| R3-INS-02 | نوع پوشش و حداقل پوشش لازم | طراحی/سیاست، G-04 باز |
| R3-INS-03 | طول شماره، مبلغ، مالیات، فیلدهای لازم | کنترل شکلی مرورگر؛ نه اعتبارسنجی سرور |
| R3-INS-04 | تاریخ، عدم هم‌پوشانی، زنجیره تمدید | تاریخ شکلی قابل آزمون؛ تمدید واقعی مسدود |
| R3-INS-05 | تعارض شماره بیمه و دوره | فقط با وثیقه واقعی و API مجاز |
| R3-INS-06 | تأیید/لغو/کفایت جهت تخصیص | G-06 باز |
| R3-INS-07 | بیمه تهیه‌شده توسط بانک | G-09 و قرارداد بیمه‌گر باز |
| R3-INS-08 | حالت صفر داده و خطای Oracle | قابل آزمون در GET-only |

نتایج هشت مورد در میزکار با پیش‌فرض `NOT_RUN`، امکان `PASS / FAIL / BLOCKED` و توضیح کوتاه ثبت می‌شوند. JSON فقط در مرورگر ساخته و صادر می‌شود؛ شواهد UAT به Backend یا Oracle ارسال نمی‌شوند. ده سناریوی رسمی UI Specification تغییر نکرده‌اند.

## مرزهای غیرقابل ادعا

- **G-04:** انواع پوشش الزام‌آور و حداقل پوشش برحسب نوع/مبلغ وثیقه مصوب نیست.
- **G-06:** مدل موجود چرخه تأیید، لغو، جایگزینی و وضعیت اعتبار بیمه‌نامه ندارد.
- **G-09:** مسیر بیمه‌نامه صادره از بیمه‌گر طرف قرارداد بانک فعال نیست.
- شرکت‌های کاندید `INACTIVE` هستند؛ `TMP-INS-1403-*` شناسه رسمی یا مجوز نیست.
- کنترل شکلیِ پیش‌نمایش محلی از `POST /validate`، ثبت `POST /requests`، شرایط CIF/شعبه، کفایت پوشش و پذیرش رسمی مستقل است. **هیچ نتیجه UAT قبل از آزمون تحلیلگر PASS فرض نمی‌شود.**

## Acceptance Gate

1. تب جدید در مرورگر باز شود بدون نیاز به شناسنامه وثیقه.
2. کاتالوگ واقعی از GET نمایش داده شود و خطای شبکه به‌جای عدد صفر گزارش شود.
3. فیلدهای عملیاتی از همان کامپوننت اصلی نمایش داده شوند، اما هیچ انتخاب نامزد غیرفعال/ارسال POST/ذخیره وجود نداشته باشد.
4. کنترل شکلی مثبت و منفی، و ثبت/خروجی JSON هشت سناریو توسط تحلیلگر بررسی شوند.
5. هیچ داده Oracle، Schema، IAM یا عملیات کسب‌وکاری تغییر نکند.

**وضعیت تحویل توسعه:** `SOURCE_QA_PASS` تنها پس از آزمون‌های بسته؛ `ANGULAR_BUILD_PENDING_WINDOWS` و `ANALYST_UAT_NOT_RUN` تا دریافت شواهد محیط واقعی.
