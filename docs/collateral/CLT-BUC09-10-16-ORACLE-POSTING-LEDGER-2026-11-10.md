# CLT — یکپارچگی ثبت Oracle و تاریخچه مالی BUC-09/10/16

**خط مبنا:** نسخه نصب‌شده `BUC09-10-ATOMIC-POSTING-HF1`، نسخه Core Banking Prototype `0.11.0`. ۱۰ نوامبر ۲۰۲۶.

## هدف و مرز تحویل

این تحویل دو شکاف عملی در مسیر نهایی تخصیص/رفع تخصیص وثیقه را می‌بندد. اول، ستون‌های الزامی جدول‌های ثبت تخصیص و تراکنش طبق قرارداد Oracle موجود نوشته می‌شوند؛ دوم، رویدادهای واقعی مالی و تاریخچه وضعیت تراکنش در گزارش BUC-16 نمایش داده می‌شوند. هیچ گیت عملیاتی یا کنترل مالی با UI تحلیلگر دور زده نشده است.

### BUC-09/10 — اصلاح ثبت تراکنشی

1. `CLT.COLLATERAL_ALLOCATION`: هنگام INSERT مقدار `CREATED_BY` از شناسه معتبر سرویس ثبت‌کننده تأمین می‌شود؛ هنگام رفع تخصیص کامل/جزئی `UPDATED_BY` نیز همان هویت تراکنش را ثبت می‌کند.
2. `CLT.COLLATERAL_TRANSACTION`: مقدارهای الزامی `SOURCE_SYSTEM_CODE`، `IDEMPOTENCY_KEY` و `CREATED_BY` افزوده شده‌اند؛ همچنین `OWNER_BRANCH_CODE`، `EXECUTING_BRANCH_CODE`، `REQUEST_ID` و زمان/نسخه به‌طور صریح درج می‌شوند.
3. `CLT.COLLATERAL_TXN_STATUS_HISTORY`: اولین وضعیت تراکنش با `STATUS_SEQUENCE_NO=1`، زمان Oracle، نام ثبت‌کننده و پیوند واقعی به تراکنش ذخیره می‌شود. درج آن در **همان تراکنش** ثبت تخصیص/رفع تخصیص، کنترل ظرفیت، افزایش نسخه وثیقه و مصرف Permit صورت می‌گیرد؛ شکست درج تاریخچه باعث Rollback کل عملیات می‌شود.
4. شماره تراکنش طبق طول فیزیکی `COLLATERAL_TRANSACTION_NUMBER VARCHAR2(64 CHAR)` محدود می‌شود.
5. مرجع `SOURCE_SYSTEM_CODE` فقط از ردیف تأییدشده `CLT.REF_SOURCE_SYSTEM` پذیرفته می‌شود. متغیر تنظیم بانک `CLT_POSTING_SOURCE_SYSTEM_CODE` عمداً خالی است؛ بدون آن و بدون تأیید Schema عملیات نهایی **Fail Closed** می‌شود.
6. کنترل پیش‌نیاز، ستون‌های اصلی و غیرNULL سه جدول را با دیکشنری Oracle تطبیق می‌دهد؛ شناسه تاریخچه باید به وسیله سازوکار Identity/Default بانک ایجاد شود.

**هیچ مجوز یا مبلغ مالی از مرورگر تحلیلگر پذیرفته نمی‌شود.** ارسال‌کننده باید JWT معتبر دامین صاحب تعهد و Permit مستقل مصوب بانک داشته باشد. هر دو Feature Flag نهایی تخصیص و رفع تخصیص همچنان `false` هستند.

### BUC-16 — تاریخچه واقعی ثبت مالی

گزارش `GET /api/v1/collaterals/reports/by-registration/{number}/history` در کنار معرفی، تغییر وضعیت، ارزیابی، بیمه، ضامن و رکورد تخصیص اکنون شامل موارد زیر نیز می‌شود:

- `TRANSACTION`: خودِ رکورد واقعی تراکنش Oracle، مبلغ، ارز، وضعیت، نوع/جهت و ارجاع به تراکنش اصلی.
- `TRANSACTION_STATUS`: سطرهای ذخیره‌شده در تاریخچه وضعیت تراکنش به همراه عامل و زمان ثبت.

هر دو Query به `authorized` با **شناسه وثیقه و شعبه احرازشده** متصل هستند. `COLLATERAL_ALLOCATION.UPDATED_AT` همچنان صرفاً «آخرین ویرایش رکورد» است و به‌اشتباه رویداد رفع تخصیص معرفی نمی‌شود. در صورت فقدان ساختار تراکنش یا تاریخچه در Oracle، گزارش پایه قبلی حفظ می‌شود و UI به‌صراحت نبود پوشش شواهد را نشان می‌دهد.

## گیت‌ها و موارد باقی‌مانده

- مدل `CLT_COVERAGE_POST_PERMIT`، شماره‌گذاری، کدهای رسمی تراکنش و مرجع دامین صاحب تعهد هنوز به تأیید بانک/DBA نیاز دارند. اسکریپت Candidate به‌صورت عمدی غیراجرایی باقی می‌ماند.
- تراز و یکپارچگی داده‌ها با Oracle زنده، Build کامل Maven/Angular در محیط Windows و UAT مثبت/منفی در UI باید در سامانه اجرایی تأیید شوند.
- BUC-11 پس از رفع کامل واقعی تخصیص‌ها و نبود Hold/مانع قانونی قابلیت بررسی دارد؛ BUC-12 و تخصیص واقعی بین‌واحدی BUC-15 همچنان از کنترل مجوز مستقل و تأیید سیاست بانک تبعیت می‌کنند.
- هیچ Migration، DML یا تغییر Feature Flag در فرایند **نصب Patch** اجرا نمی‌شود.

## شواهد QA محلی

- ۴۲ کنترل قرارداد سورس و متادیتای ستون‌های Oracle.
- ۲۳ Assertion برای اجرای Repository با JDBC شبیه‌سازی‌شده و کنترل آرگومان‌های bind.
- ۱۱ آزمون مثبت/منفی قرارداد Frontend برای دو رخداد مالی جدید.
- Typecheck Java 21 با وابستگی‌های Spring/JDBC شبیه‌سازی‌شده و کنترل نحو ۲۴۸ فایل Java وثایق.
- کنترل TypeScript و Imports و اجرای آزمون‌های بازگشتی پیشین بدون شکست.
- آزمون SHA-guarded Installer، بازگردانی، نصب تکراری، حفظ سه فرم سفارشی.

این تحویل **شاهد اجرای زنده Oracle نیست**؛ تا زمان تأیید پیش‌نیازها ثبت مالی پیش‌فرض غیرفعال خواهد ماند.
