# CLT-R2-R3-Consolidated — ادامه فازهای شناسنامه، معرفی و اجزای تخصصی

**تاریخ:** ۱۴۰۵/۰۸/۱۷ — 2026-11-08  
**نسخه نرم‌افزار:** `0.11.0` (بدون تغییر نسخه محصول)  
**Baseline نصب:** سورس 2026-11-08 12:19 به‌علاوه System UI V1، HF1، CLT-R1-Closure و CLT-R1-17-Table-UAT-Matrix  
**مرجع ثابت:** `docs/collateral/CLT-ROADMAP-R1.0-FA.md`؛ R0 تا R7 بدون تغییر نام، دامنه یا ترتیب.

## هدف و تغییر واقعی

### R2 — جست‌وجوی شناسنامه و بازیابی واقعی

- فیلترهای سمت سرور برای **شماره انتظامی، گروه وثیقه، نوع وثیقه، شناسه شخص و وضعیت** به API فهرست شعبه اضافه شد. شرط‌ها پارامتری‌اند و شعبه همچنان از نشست سرور استخراج می‌شود؛ هیچ نوع، کد، شناسه یا شرط SQL از UI مستقیماً در متن SQL تزریق نمی‌شود.
- فهرست وضعیت‌ها از `CLT.REF_COLLATERAL_STATUS` (فقط مرجع فعال) و نوع‌ها از `CLT.COLLATERAL_TYPE` دریافت می‌شود؛ گزینه ساختگی یا وضعیتی که در مرجع وجود ندارد تولید نمی‌شود.
- عنوان وضعیت بر مبنای `COLLATERAL_STATUS_NAME` در فهرست و شناسنامه به‌صورت کسب‌وکاری نمایش داده می‌شود. کد فنی و کلیدهای داخلی در `<details>` حسابرسی هستند، نه در ردیف‌های اصلی.
- نمایش تاریخ‌های موجود بدون تغییر قرارداد Oracle/JSON، با تقویم شمسی و حفظ wall-time/ثانیه انجام می‌شود. این فرمت، تغییر SQL `DATE` یا `TIMESTAMP` نیست.
- فهرست و جزئیات همواره توسط API دارای `BRANCH_CODE` سروری بازیابی می‌شوند؛ نتیجه دستی/موقت مرورگر به‌جای رکورد واقعی جا زده نمی‌شود.

### R3 — پیش‌نویس معرفی، محدود به ساختار مرحله‌ای موجود

- در **حالت Unified محلی روی `127.0.0.1`**، Writer پیش‌نویس می‌تواند از همان `DataSource` مشترک برنامه استفاده کند؛ اطلاعات اتصال جدید، Starter مستقل یا نام کاربری جداگانه تعریف نمی‌شود.
- اجازه POST دقیقاً به مسیر `POST /api/v1/collaterals/introduction-drafts` محدود می‌شود؛ ثبت قطعی در `CLT.COLLATERAL`، تخصیص، رفع تخصیص و آزادسازی همچنان ممنوع است.
- پیش از نشان‌دادن آمادگی ثبت، وجود دو جدول **مرحله‌ای مصوب**، Sequence پیش‌نویس و ستون‌های لازم از `ALL_*` Oracle کنترل می‌شود؛ نبودن هر جزء یا نسخه ناقص افزونه R2C، `draftWritesEnabled=false` و خطای روشن آمادگی ایجاد می‌کند. این بررسی هیچ DDL یا DML ندارد.
- پس از POST پیش‌نویس، `GET` مستقل با شناسه برگشتی باید شناسه، مالک، نوع وثیقه، نسخه و وضعیت `DRAFT` را تأیید کند؛ قبل از آن موفقیت قطعی در UI اعلام نمی‌شود.
- گردش Maker/Checker در این حالت محلی فعال نشده است. تأیید صلاحیت بانک/بیمه‌گر، شماره انتظامی نهایی و گیت‌های کسب‌وکاری همان مسیر سابق را دارند.

## آنچه عمداً انجام نشده است

- **هیچ DDL خودکار** روی Oracle اجرا نمی‌شود. فایل‌های قدیمی `database/oracle/clt/r2b` و `r2c` همچنان Candidate / DBA Opt-in هستند؛ این Patch آن‌ها را تغییر یا اجرا نمی‌کند.
- اگر ساختار مرحله‌ای در بانک نصب نشده باشد، پیش‌نویس **ثبت نخواهد شد**؛ صرف موفقیت Build، مجوز ایجاد ساختار نیست.
- ثبت و ویرایش قطعی شناسنامه وثیقه، الگوریتم شماره انتظامی G-17، وضعیت `PENDING/PENDING_APPROVAL` (G-16)، گردش مصوب G-15 و سیاست‌های G-10 همچنان باز هستند.
- عملیات تخصصی ضامن، بیمه و ارزیابی که نیازمند تصمیم یا Writer اختصاصی هستند، با این Patch فعال نمی‌شوند. تب‌های موجود R3 حفظ می‌شوند؛ پذیرش عملیاتی آن‌ها ادعا نمی‌شود.
- IAM، مسیرهای سایر ماژول‌ها، Schema پایه، JAR Launcher و تنظیمات مشترک اتصال تغییر داده نشده‌اند.

## پذیرش مورد انتظار تحلیلگر (بدون آزمون فنی جداگانه)

۱. در «فهرست وثایق»، فیلتر گروه، نوع، شخص و وضعیت را از UI اعمال کند؛ مشخص شود همه نتایج به همان شعبه و شرط‌ها متعلق‌اند. نبودن رکورد به‌عنوان نبود داده گزارش شود، نه Mock.
۲. شماره انتظامی موجود را بازیابی و عنوان وضعیت، تاریخ شمسی و بخش فنی بازشونده شناسنامه را بررسی کند.
۳. در «معرفی وثیقه» اگر ساختار مرحله‌ای آماده باشد، پیش‌نویس آزمایشی را ثبت کند و پیام تأیید بازیابی مستقل را مشاهده کند؛ در غیر این صورت وضعیت «ساختار مرحله‌ای آماده نیست» را به‌عنوان گیت باز ثبت کند.
۴. عدم صدور شماره انتظامی/ثبت نهایی، و عدم دسترسی به تخصیص و آزادسازی از مسیر جدید را تأیید کند.
