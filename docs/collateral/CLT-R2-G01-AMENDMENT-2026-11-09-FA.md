# CLT-R2-G01 — چرخه درخواست اصلاحیه شناسنامه وثیقه

- تاریخ: 2026-11-09
- فاز ثابت: **R2 — شناسنامه، معرفی و جست‌وجو**؛ نقشه راه `CLT-ROADMAP-R1.0-FA.md` تغییر نکرده است.
- منبع: `BUC-05 / SUC-05 / SUC-06 / SVC-03 / SVC-04` و Gap Register G-01.
- وضعیت: **پیاده‌سازی سورس + Migration پیشنهادی آماده؛ استقرار دیتابیس، Build ویندوز و UAT انجام‌نشده**؛ G-01 تا تأیید طراحی/اجرای Migration و آزمون عملیاتی بسته نمی‌شود.

## محدوده پیاده‌سازی

- `GET /api/v1/collaterals/amendments/readiness`: وضعیت فعال‌سازی صریح، بدون ساخت خودکار جدول.
- `GET /api/v1/collaterals/{id}/amendments`: تاریخچه ۵۰ درخواست اخیر وثیقه در شعبه جاری.
- `POST /api/v1/collaterals/{id}/amendments`: ثبت درخواست `PENDING_REVIEW` در جدول مستقل بدون هیچ تغییر در `CLT.COLLATERAL`.
- `POST /api/v1/collaterals/{id}/amendments/{amendmentId}/decision`: تصمیم بازبین مستقل؛ تأیید فقط در صورت صحت نسخه، سلامت پیشنهاد، نبود سابقه وابستگی و `ACTIVE` بودن وثیقه؛ اعمال تغییر شناسنامه، به‌روزرسانی درخواست و درج Audit در یک تراکنش JDBC.
- فرم «اصلاحیه شناسنامه» از جزئیات وثیقه؛ انتخاب فیلد، ارائه دلیل، نمایش صف و سوابق، و دکمه تصمیم بازبین.
- چهار فیلد مجاز: `ESTIMATE_AMOUNT`, `VALID_TO`, `DEPOSIT_NUMBER`, `REMARKS`. هر فیلد دیگر رد می‌شود. شناسه، شماره انتظامی، Party، نوع وثیقه، تاریخ شروع، شعبه، ارز و وضعیت تغییرناپذیرند.
- وجود **هرگونه** سابقه در `COLLATERAL_SPONSOR`, `COLLATERAL_INSURANCE`, `COLLATERAL_VALUATION_HISTORY`, `COLLATERAL_ALLOCATION`، نه‌فقط رکورد فعال، مانع درخواست و تأیید می‌شود.
- API Idempotency-Key را برای دو فرمان می‌پذیرد؛ `RECORD_VERSION` شناسنامه و اصلاحیه کنترل می‌شود. مشخصات Before/After و Audit قابل ردیابی‌اند.

## مرز کنترل‌های عملیات

- Migration پیشنهادی در `database/clt/r2-g01-amendments/001_CREATE_AMENDMENT_REQUEST.sql` مستقل از EA XML است؛ پس از تصویب Change Control باید در Oracle اجرا و در مدل EA/DB Specification ثبت شود. نصاب این SQL را اجرا نمی‌کند.
- از DataSource مشترک برنامه استفاده می‌شود؛ Oracle Connection/User/Pool جدید وجود ندارد.
- `CLT_G01_WRITES_ENABLED` فقط مسیر نوشتن همین جدول‌ها و تصمیم را کنترل می‌کند، اما حتی در صورت فعال‌بودن، فقدان جدول به‌صورت fail-closed گزارش می‌شود.
- در Prototype تک‌کاربره هویت Maker ثابت است؛ بازبینی توسط همان هویت صراحتاً ممنوع است. هیچ جعل هویت Checker یا دورزدن تفکیک وظایف انجام نمی‌شود. اتصال مجوزهای سازمانی فقط در فاز یکپارچه‌سازی قرار می‌گیرد.
- ساخت شناسنامه جدید، صدور شماره انتظامی و رفع G-17 جزء این Patch نیست.
- هیچ Oracle DDL/DML در زمان نصب سورس، هیچ تغییر در IAM، هیچ تغییر در R1/لوگو، و هیچ Starter مستقل وجود ندارد.
- UI/UAT و اجرای Oracle در انتهای توسعه طبق تصمیم تیم انجام خواهد شد.

## پیش‌شرط و وابستگی

۱. خط مبنای تأییدشده نصب قبلی `CLT-R2-ASSET-CANDIDATE-G14-2026-11-09`.
۲. تصویب Migration و اعمال دستی/کنترل‌شده آن یک‌بار روی `CLT`؛ بدون DDL خودکار از Backend یا نصب کننده.
۳. برای پیشنهاد، شناسنامه ACTIVE موجود با دسترسی شعبه، بدون هر وابستگی عملیاتی.
۴. برای تصمیم، حساب مستقل با مجوز `SCOPE_clt.collateral.review` در محیط نقش‌دار؛ در Prototype محلی تک‌کاربره صدور تصمیم مجاز نیست.
