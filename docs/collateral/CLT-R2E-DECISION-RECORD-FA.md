# CLT R2E — پرونده تصمیم معماری ثبت قطعی وثیقه

**مرجع:** `CLT-ROADMAP-R1.0`؛ **مرجع رفتار:** `Collateral_UI_Final_Offline_V1.42_FA.html`؛ **مدل:** `Collateral_EA_Model_Candidate.xml`، خروجی `CLT-2026-11-1.txt` و SQL فیزیکی. **وضعیت:** پیشنهاد برای تصویب بانک و DBA، نه سیاست مصوب.

## ۱. مسئله و حدود اختیار

ثبت قطعی تنها پس از طی زنجیره `DRAFT → PENDING_REVIEW → REVIEWED → [Final Registration]` ممکن است. `REVIEWED` بازبینی پیش‌نویس است، نه مجوز مالی یا صدور شماره. ثبت نهایی باید شناسنامه، ویژگی‌ها، اقلام، هویت دارایی، شماره یکتا، تاریخچه و رکورد تراکنش را یکجا و به‌صورت اتمیک ثبت کند. R2E فعلاً صرفاً گزارش شواهدِ نسخه ذخیره‌شده را تولید می‌کند و **هیچ نویسنده‌ای روی جدول اصلی** ندارد.

### بررسی ظرفیت G-17

اگر طول کد نوع = **T** و طول شماره مشتری = **C** باشد، طول کل الگوریتم نمونه UI برابر `T + 4 + C + 3 + 1 = T+C+8` است. شرط جا شدن در `NUMBER(19)` برابر `T+C <= 11` است. برای مثال T=3 و C=8 به ۱۹ رقم می‌رسد، اما T=5 و C=8 به ۲۱ رقم می‌رسد و قابل ذخیره در ستون فعلی نیست. این **مثال محاسباتی است، نه تأیید طول شناسه مشتری در CIF**. صفرهای ابتدای شماره، و تبدیل به `JavaScript Number` نیز باید جداگانه بررسی شوند. ظرفیت ترتیب ۳رقمی **۹۹۹** مورد در هر کلید صدور است.

## ۳. مرزهای Ownership و API

- `CIF` مالک Party و شماره مشتری معتبر باقی می‌ماند؛ CLT حق ایجاد Customer/Party جدید ندارد.
- `CLT` مالک Collateral Master، هویت/پیوست دارایی، شماره ثبت، ویژگی‌ها و تاریخچه است.
- سیستم‌های تسهیلات، سپرده و سایر مصرف‌کنندگان فقط از قرارداد مستقل درخواست تخصیص استفاده می‌کنند؛ **R2E هیچ تخصیص، Hold، Posting یا ثبت مالی انجام نمی‌دهد**.
- در صورت تصویب ثبت قطعی، مجوز مجزا `clt.collateral.register` با هویت JWT، شعبه، جداسازی نقش و Idempotency لازم است؛ مجوز بازبینی `clt.collateral.review` به‌تنهایی کافی نیست.

## ۴. بسته پیشنهادی Data Model

فایل `database/oracle/clt/r2e/01_REGISTRATION_MODEL_CANDIDATE_NOT_APPROVED.sql` پنج جدول پیشنهادی `CLT_ASSET_IDENTITY`، `CLT_ASSET_COLLATERAL_LINK`، `CLT_COLLATERAL_SERIAL_RANGE`، `CLT_REGISTRATION_LEDGER` و `CLT_REGISTRATION_NUMBER_AUTHORITY` را ارائه می‌کند. **این فایل نه مصوب است و نه از Installer اجرا می‌شود.** تغییر پایه ۲۶جدولی EA، وضعیت Audit و نوع/طول شماره باید پیش از اجرای آن با بانک/DBA تطبیق یابد. علاوه بر این، G-01 به طراحی کامل اصلاحیه نیاز دارد.

## ۵. قرارداد اتمیک برای مرحله پس از تصویب

۱. احراز `SCOPE_clt.collateral.register` از JWT و استخراج شعبه از Claim معتبر؛ جلوگیری از ثبت به نام کاربر دیگر.
۲. در یک Transaction، قفل‌گذاری بر `REVIEWED`، Draft و Asset؛ تطبیق Snapshot Hash و کنترل آخرین اطلاعات CIF و CLT.
۳. کنترل یکتایی دارایی، عدم وجود معرفی فعال، وضعیت اصلاحیه و عدم تداخل اقلام با قفل مناسب.
۴. رزرو شماره از Authority مصوب با کلید شناسه بازبینی و `FOR UPDATE SKIP LOCKED`؛ عدم پذیرش شماره از Client و بررسی اندازه Oracle و Unique.
۵. Insert شناسنامه `CLT.COLLATERAL`، مقادیر Attribute، اقلام، ارتباط Asset، رویداد وضعیت و `INTRODUCTION` با کد وضعیت **صریح و معتبر**، Ledger ثبت و Audit.
۶. Commit یکجا؛ هر شکست Rollback کامل. Replay با کلید/Hash مشابه همان نتیجه را برمی‌گرداند و Replay نامتجانس `409` می‌شود. هیچ شماره‌ای بعد از صدور/لغو به چرخه بازنمی‌گردد.
۷. UAT: ثبت عادی، بازبینی توسط شخص مستقل، تکرار درخواست، رقابت دو شعبه بر یک Asset، تداخل سریال، سطر ناقص، طول ۱۹/۲۰/۲۱ رقم، توقف Oracle وسط تراکنش، عدم اعتبار CIF، و فعال‌سازی نشدن خودکار تخصیص.

## ۶. تصمیم برای این تحویل

- **R2E:** API GET گزارش آمادگی مبتنی بر پیش‌نویس ذخیره‌شده و بازبینی‌شده؛ کنترل تمامیت، بازاعتبارسنجی، دیکشنری Oracle و ماتریس تصمیم در UI. بدون تغییر Oracle یا IAM.
- **ثبت قطعی:** همچنان Fail-Closed. هیچ Feature Flag ساده‌ای نمی‌تواند این شکاف‌های کسب‌وکار را نادیده بگیرد.
- **پیشنهاد تصویب:** بانک درباره سیاست شماره‌گذاری، مرجع شناسایی دارایی، رفتار شمارشی، اصلاحیه و هماهنگی کدهای تراکنش تعیین تکلیف کند. پس از آن پیاده‌سازی Transaction واقعی (در همان فاز R2) و آزمون UAT انجام شود.

**این تصمیم، نام یا محدوده فازهای مصوب R0 تا R7 را تغییر نمی‌دهد.**
