# قرارداد فنی R5C — شواهد آزادسازی نهایی و تاریخچه وضعیت وثیقه

**نسخه:** R5C.1.0 — **تاریخ:** ۱۴۰۵/۰۸/۱۳ (2026-11-04) — **مرجع ثابت:** `CLT-ROADMAP-R1.0` — **پیش‌نیاز:** سورس R5B روی Core Banking Prototype `0.11.0`.

## ۱. هدف و قلمرو

R5A سوابق تخصیص و پیش‌بررسی رفع تخصیص را ایجاد کرد. R5B چرخه **درخواست مرحله‌ای رفع تخصیص** را با حالت‌های `RECORDED_NOT_UNALLOCATED` و `CANCELLED_NOT_UNALLOCATED` طراحی کرد. R5C بر **آزادسازی نهایی کل وثیقه** تمرکز دارد. آزادسازی نهایی تنها پس از پایان تمام تعهدات و موانع حقوقی قابل بررسی است و با لغو درخواست رفع تخصیص یا صرف مشاهده `USED='NO'` یکسان نیست.

R5C در این تحویل **فقط شواهد، تاریخچه و پیش‌نمایش بازدارنده** را ارائه می‌دهد؛ **هیچ درخواست آزادسازی پایدار، تغییر وضعیت `COLLATERAL`، درج در `COLLATERAL_TRANSACTION`، تغییر `USED` یا به‌روزرسانی `COLLATERAL_STATUS_HISTORY` اجرا نمی‌شود.** آزادسازی از نظر کسب‌وکار و عملیات مالی «پیاده‌سازی‌نشده/غیرفعال» است.

## ۲. منبع داده واقعی و قواعد عدم استنتاج

| داده واقعی CLT | استفاده در R5C | محدودیت |
|---|---|---|
| `COLLATERAL` | شعبه مجاز، شناسه، شماره انتظامی، کد وضعیت، `RECORD_VERSION` | وضعیت گزارش‌شده، گواه آزادسازی نیست |
| `COLLATERAL_TYPE.REQUIRED_RELEASE_INQUIRY` | اعلام لزوم استعلام آزادسازی برای نوع وثیقه | `N` به معنای تأیید حقوقی نیست |
| `REF_COLLATERAL_STATUS.IS_TERMINAL_STATUS_FLAG` | اطلاع از پرچم خاتمه | حتی ترمینال بودن اثبات پایان تعهد نیست |
| `COLLATERAL_ALLOCATION` | تعداد کل، فعال `USED='YES'`، مغایرت شعبه، مقدار نامعتبر `USED` | `USED='NO'` علت یا قطعی شدن رفع تخصیص را اثبات نمی‌کند |
| `COLLATERAL_TRANSACTION` | شمارش تراکنش `PENDING` به‌عنوان شاهد مانع | نبود `PENDING` اثبات تسویه کل تعهدات نیست |
| `COLLATERAL_STATUS_HISTORY` | مشاهده تغییرات وضعیت و شواهد منبع ثبت | تنها داده موجود در Oracle را نمایش می‌دهد |

سرور در تمام درخواست‌های محتوایی ابتدا JWT با Scope `clt.collateral.read` و `branch_code` معتبر را کنترل کرده و سپس با `CollateralRegistryRepository.byId` وجود وثیقه در شعبه را تأیید می‌کند؛ فقدان وثیقه و عدم دسترسی شعبه هر دو 404 هستند. شناسه‌های ۱۹رقمی به‌صورت رشته جابه‌جا می‌شوند.

**نکته تراکنشی:** شواهد چند Query مستقل و صرفاً خواندنی هستند. این Snapshot اتمیک بین دیتابیس‌ها/دامین‌ها نیست؛ بنابراین حتی با صفر شدن همه شمارنده‌ها نتیجه `DENIED` تغییر نمی‌کند.

## ۳. قرارداد API جدید

| HTTP | مسیر | سطح مجوز | اثر |
|---|---|---|---|
| GET | `/api/v1/collaterals/{id}/final-release/readiness` | JWT + `SCOPE_clt.collateral.read` | وضعیت پیکربندی، بدون خواندن وثیقه |
| GET | `/api/v1/collaterals/{id}/final-release/evidence` | JWT + Branch + READ | شواهد مالی، وضعیت، موانع |
| GET | `/api/v1/collaterals/{id}/final-release/status-history?limit=20` | JWT + Branch + READ | حداکثر ۵۰ رویداد تاریخچه |
| POST | `/api/v1/collaterals/{id}/final-release/preview` | JWT + Branch + READ | محاسبه فقط خواندنی؛ **بدون ثبت** |

پیش‌بررسی نیازمند `Idempotency-Key` با UUID معتبر، `If-Match: "<RECORD_VERSION>"` قوی و Body مانند `{ "reasonReference": "ANALYST_RELEASE_PREVIEW" }` است. کلید، Digest تشخیصی تولید می‌کند اما **هیچ Idempotency پایدار یا Receipt بانکی** ایجاد نمی‌شود. شناسه نسخه از Oracle به‌دست می‌آید و در پاسخ بررسی می‌شود.

**هر پاسخ:** `releaseAuthorized=false`, `finalReleaseAuthorized=false`, `capacityReleased=false`, `durableRequestRecorded=false` در فیلد مربوطه؛ حتی اگر شمارنده فعال صفر باشد. مسیر `POST /final-release/commit` عمداً وجود ندارد.

## ۴. نمودار منطقی تصمیم

1. احراز JWT، Scope و Branch در سرور، سپس خواندن وثیقه در شعبه مجاز.
2. خواندن وضعیت فعلی و `RECORD_VERSION`؛ خواندن تعداد تمام تخصیص‌ها و تخصیص‌های فعال، تخصیص با شعبه متفاوت و `USED` نامعتبر.
3. شمارش تراکنش‌های `PENDING`؛ خواندن پرچم نیاز به استعلام حقوقی و تاریخچه وضعیت.
4. اعمال `If-Match` قوی در Preview؛ در اختلاف نسخه، مانع `CLT_R5C_COLLATERAL_VERSION_MISMATCH` تولید می‌شود، بدون Write.
5. ارزیابی موانع ثابت: عدم تأیید تعهد دامین مصرف‌کننده (G-09)، مجوز بین‌شعبه‌ای (G-13)، Ledger و رفع تخصیص مالی (G-20)، نبود اتصال حقوقی/وثیقه‌های DPS2 (G-21)، Snapshot غیراتمیک و خاموش بودن Write.
6. بازگشت `DENIED_NO_FINAL_RELEASE_OR_STATUS_MUTATION`. **هیچ عمل جانبی انجام نمی‌شود.**

## ۵. شکاف‌های باز و شروط لازم پیش از آزادسازی واقعی

- **G-09:** تأیید معتبر از همه دامین‌های مصرف‌کننده مبنی بر خاتمه تعهد.
- **G-13:** مدل مجوز شعبه، صاحب تعهد و واحد اجراکننده.
- **G-19:** نگاشت مصوب `consumerDomain -> MODULE_ID` در رفع تخصیص.
- **G-20:** قرارداد مالی FULL/PARTIAL، Audit، Ledger، Reversal و Posting.
- **G-21 (جدید):** قرارداد رسمی استعلام قضایی، توقیف حقوقی، وثایق و Holdهای DPS2، و منبع قابل اتکا برای تأیید نبود مانع آزادسازی.
- **G-22 (جدید):** نگاشت و تصویب کدهای نهایی `REF_COLLATERAL_STATUS`، نوع/وضعیت تراکنش آزادسازی، کنترل زنجیره تاریخچه و پروتکل شماره انتظامی جدید در معرفی مجدد؛ صرف ترمینال بودن یک کد کافی نیست.
- آزمون دو Session Oracle برای قفل مشترک `COLLATERAL`، اتمیک‌بودن Ledger + Status History و Rollback اجباری است؛ هیچ مسیر نصب/Build جای آن را نمی‌گیرد.

## ۶. محافظت کد و انتشار

- فقط زیرماژول `collateral/release` و سه فایل موجود متعلق به Collateral (`CollateralRegistrySecurityConfiguration`, `collateral-registry.component.ts`, `.html`) تغییر می‌کنند.
- فرانت‌اند در همان شناسنامه، بخش «آزادسازی نهایی» را نمایش می‌دهد؛ هیچ Route سراسری یا مسیر IAM/CIF/DPS2 تغییر نمی‌کند.
- کنترل SQL فقط‌خواندنی برای DBA در `r5c/00_*.sql`؛ فایل `r5c/01_*.sql` با `RAISE_APPLICATION_ERROR(-20956)` متوقف می‌شود و فاقد دستور مالی قابل اجرا است.
- پیش‌نیاز R5B: آخرین بسته R5B باید قبلاً نصب شده باشد. **این سند موفقیت Build R5B را مفروض نمی‌گیرد.**

## ۷. وضعیت کلی

R5C تکمیل فنی لایه شواهد آزادسازی است، نه پایان عملیاتی R5. تکمیل بخش UI و UAT در R6، و یکپارچه‌سازی/امنیت/آمادگی عملیاتی در R7 طبق نام فازهای ثابت `CLT-ROADMAP-R1.0` ادامه می‌یابد. برای UAT عملیاتی، تأیید بانک و DBA لازم است.
