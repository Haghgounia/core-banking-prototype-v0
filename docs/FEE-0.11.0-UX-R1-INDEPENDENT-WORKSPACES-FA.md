# FEE UX R1 — بازطراحی مستقل رابط مدیریت کارمزد

تاریخ: ۱۴۰۵/۰۷/۱۹ (2026-10-11)  
نسخه مبنا: `core-banking-prototype-v0-2026-10-11-1311.zip`  
مسیر اصلی: `/fee` | مرجع یکپارچه: `/fee/references`

## اصل غیرقابل تغییر

FEE و FEE2 **دو ماژول مستقل** با Schema، API، مدل داده، منطق و مسیر اختصاصی هستند. نه ادغام می‌شوند و نه یکی به‌عنوان مرجع دیگری انتخاب می‌شود. این Patch تنها به FEE و تنظیمات مسیرهای آن می‌پردازد و هیچ‌یک از منابع اختصاصی FEE2 را تغییر نمی‌دهد. نیازی به DDL یا Migration داده‌ای نیست.

## محدوده اصلاحات انجام‌شده

۱. **صفحه اصلی FEE**: به‌جای نمایش همزمان همه ۴۷ فرم فنی، ۸ محیط کاری کسب‌وکارمحور نمایش داده می‌شود. فهرست فنی کامل و دیاگرام ۹گام قدیمی در پنل‌های بازشونده باقی می‌مانند. وضعیت جداول از همان API `/api/v1/fees/admin/catalog` گرفته می‌شود.

۲. **محیط‌های کاری جدید**: `/fee/workspaces/:workspace` فهرست مرحله‌ای جدول‌های یک حوزه را نشان می‌دهد؛ ۴۷ جدول دقیقاً یک‌بار در این هشت محیط نگاشت شده‌اند. پوشش فعلی به معنای تبدیل تمام فرم‌ها به یک Wizard واحد نیست: ۴۵ جدول غیرمرجع همچنان با همان فرم نگهداری قبلی باز می‌شوند. هیچ مسیر قبلی حذف نشده است.

۳. **مرجع یکپارچه FEE**: `/fee/references` با الگوی Master–Detail، انتخاب و جستجوی دامنه و نمایش فقط مقادیر `DOMAIN_ID` مربوط به دامنه را ممکن می‌کند. افزودن/ویرایش دامنه و مقدار، تعیین مقدار والد صرفاً از همان دامنه، تاریخ‌های اعتبار شمسی و تفکیک وضعیت معتبر/منقضی/آینده، جستجو و صفحه‌بندی انجام می‌شود. داده‌ها همچنان در `FEE.FEE_REF_DOMAIN` و `FEE.FEE_REF_VALUE` ذخیره می‌شوند.

۴. **کنترل حذف اطلاعات پایه**: رابط جدید فقط امکان فعال/غیرفعال‌سازی (`IS_ACTIVE`) دارد و حذف فیزیکی ندارد. در دو فرم قدیمی مرجع نیز دکمه حذف پنهان شده، اما API عمومی حذف تغییر نکرده است. این اصلاح UI به‌تنهایی کنترل دسترسی امنیتی و Maker–Checker محسوب نمی‌شود.

۵. **Cache / اعتبار Lookups**: هر تغییر دامنه یا مقدار، Metadata Cache داخل FEE Admin Backend را باطل می‌کند تا انتخابگرهای بازشده پس از درخواست جدید، کدهای تازه را دریافت کنند. گزینه‌های `FEE_REF_VALUE` از نظر فعال بودن و محدودیت `EFFECTIVE_FROM/EFFECTIVE_TO` کنترل می‌شوند. بازکردن مجدد فرم دیگر ممکن است برای مشاهده گزینه‌های جدید لازم باشد.

۶. **فرم‌های فنی**: Breadcrumb به محیط کاری همان جدول برمی‌گردد و نام‌های فیزیکی ستون‌ها، نوع داده و جزئیات FK با کلید نمایش مشخصات فنی قابل مشاهده‌اند؛ به‌طور پیش‌فرض پنهان‌اند. برای ۱۲ جدول Runtime حالت فقط‌خواندنی حفظ شده است.

## راهنمای نصب

۱. از پروژه و تنظیمات `config` نسخه پشتیبان بگیرید.  
۲. Backend را از طریق اسکریپت مدیریتی خود متوقف کنید؛ سپس **Patch ZIP** را در ریشه `D:\Projects\core-banking-prototype-v0` استخراج کنید، به‌گونه‌ای که ساختار `frontend/`, `backend/`, `tools/` در ریشه پروژه قرار بگیرد.  
۳. در CMD اجرا کنید:

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\verify-fee-admin-baseline.mjs
node tools\verify-fee-ux-r1.mjs
node tools\verify-fee2-forms.mjs
node tools\verify-fee2-studio.mjs
build-production.cmd
bin\start.cmd
```

۴. در صورت عدم اجرای صحیح Build، از راه‌اندازی JAR قدیمی به‌عنوان تأیید Patch خودداری کنید. این تغییر به Frontend و Backend جدید نیاز دارد.

## کنترل دستی / UAT

- در `/fee` هشت کارت ببینید؛ با بازکردن «نمایش ۴۷ فرم» مطمئن شوید دسترسی به همه جداول حفظ شده است.
- در `/fee/references` یک دامنه را انتخاب کنید؛ مقادیر دامنه دیگر نباید در سمت راست ظاهر شوند.
- جستجوی نام/کد دامنه، جستجوی مقادیر، صفحه‌بندی و ثبت/ویرایش را آزمایش کنید.
- مقادیر جدید به‌طور خودکار `DOMAIN_ID` انتخاب‌شده را دریافت کنند. مقدار والد از دامنه دیگر قابل انتخاب نباشد.
- قبل از تغییر کدهای واقعی، با رکورد آزمایشی مجاز در محیط تست کنترل کنید. غیرفعال‌سازی کد باید پس از بازکردن مجدد فرم وابسته در Lookup بازتاب یابد.
- دو URL قبلی `/fee/tables/FEE_REF_DOMAIN` و `/fee/tables/FEE_REF_VALUE` همچنان باز شوند؛ دکمه حذف آنها دیده نشود.
- از یک فرم در `/fee/workspaces/calculation` به صفحه فرم رفته و از Breadcrumb به همان محیط برگردید.
- ۱۲ جدول `/fee/workspaces/runtime` فقط مشاهده باقی بمانند.
- `/fee/simulator` حفظ شود؛ ذخیره پیش‌نویس هنوز Persistence عملیاتی ندارد.
- در `/fee2/studio` و `/fee2/tables/...` رفتار و ظاهر پیشین بدون تغییر باقی بماند.

## وضعیت آزمون و محدودیت

`verify-fee-admin-baseline.mjs`، `verify-fee-ux-r1.mjs`، `verify-fee2-forms.mjs` و `verify-fee2-studio.mjs` در محیط تولید Patch قابل اجرا و Pass هستند. Syntax فایل‌های جدید TypeScript نیز کنترل شد. **کامپایل کامل Angular و Spring Boot یا آزمون Oracle Runtime در این محیط انجام نشده** چون وابستگی‌های Frontend به‌طور کامل در Cache نصب نبودند و npm registry در دسترس نبود. نتیجه نهایی نیازمند Build و UAT در محیط ویندوز پروژه است.

## گام بعدی (جدا از R1)

پس از قبول R1 در UAT می‌توان فرم‌های قواعد و محاسبه را به Designerهای هوشمند تبدیل کرد و برای تنظیمات حساس از مجوزهای مناسب و Maker–Checker استفاده کرد؛ بدون دست‌کاری در FEE2.
