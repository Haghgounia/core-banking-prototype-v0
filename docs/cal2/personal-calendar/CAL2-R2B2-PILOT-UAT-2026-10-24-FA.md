# CAL2 R2-B2 — پچ آزمایشی تقویم شخصی، متصل به شش جدول نصب‌شده

**وضعیت:** Source Candidate / نیازمند Build کامل و آزمون عملی Oracle؛ **مجوز انتشار عملیاتی بانک نیست**.

**مبنا:** `core-banking-prototype-v0-2026-10-24-0748.zip` و ساختار واقعی `CAL2` که کاربر در خروجی Data Dictionary در ۲۴ اکتبر ۲۰۲۶ ارائه کرده است.

## محدوده تغییر

- **پایگاه داده:** هیچ جدول، Sequence، Index یا داده‌ای در این Patch ایجاد/حذف/تغییر نمی‌شود. R2-B1 قبلاً روی Oracle نصب شده است.
- **Backend جدید:** بسته مستقل `calendar2.personalv2`، REST `/api/v2/calendar2/personal`، مالکیت با زوج Issuer/Subject، کلیدهای Decimal String، `Idempotency-Key` برای Create، Optimistic Lock (`If-Match`)، Soft Cancel و تغییر وضعیت هر Occurrence.
- **اعلان‌ها:** `AT_DUE` + پیش‌آگاهی `DAILY_WINDOW` یا `SINGLE_OFFSET`؛ Inbox ماندگار در Oracle، تأیید Alert مستقل، Snooze و بازفعال‌سازی در Scheduler سروری.
- **تکرار:** Daily/Weekly/Monthly/Yearly با Calendar Variant انتخاب‌شده و Lookup از `CALENDAR_DATE`، تولید افق ۹۰ روز، کلید Original Slot قطعی. ماسک هفتگی ISO دوشنبه تا یکشنبه. سیاست `SKIP` و `LAST_DAY_IF_INVALID` برای تکرار ماهانه و سالانه.
- **Frontend:** یادداشت، کار، قرار ملاقات؛ ساعت شروع مستقل از ساعت یادآوری؛ تنظیم تکرار و شروع پیش‌آگاهی؛ Inbox با کلید مستقل Alert و دکمه «۱۵ دقیقه بعد».
- **محدوده ثابت:** هیچ Repository/DDL مربوط به رویدادهای رسمی، مناسبت‌ها و تقویم کاری تغییر نکرده است.

## فعال‌سازی ساده فقط برای محیط آزمایشی تک‌کاربره

به‌صورت پیش‌فرض دسترسی بدون Principal احراز هویت‌شده **بسته** است. برای استفاده محلی کنترل‌شده، در CMD همان پنجره‌ای که **Backend را اجرا می‌کنید**:

```cmd
set CAL2_PERSONAL_R2B2_DEMO_ENABLED=true
```

سپس سورس را از ریشه با `build-production.cmd` بسازید و سرویس را با `bin\start.cmd` راه‌اندازی کنید. همین یک متغیر، Scheduler تقویم شخصی را هم فعال می‌کند، مگر `CAL2_PERSONAL_R2B2_SCHEDULER_ENABLED` جداگانه تنظیم شده باشد. در حالت عادی، بدون این متغیر، کاربر غیرمعتبر `401` دریافت می‌کند.

> این حساب آزمایشی، IAM بانکی نیست. **پیش از چندکاربره یا Production:** اتصال واقعی Spring Security/Principal، issuer مورد اعتماد، حساب Oracle با حداقل دسترسی، وضعیت اتصال پیش‌فرض `SYSTEM` و ذخیره گذرواژه ثابت باید اصلاح شود. نام صاحب داده هرگز از بدنه Request اخذ نمی‌شود.

## نصب و کنترل پیشنهادی

1. در SQL Developer با کاربر دارای دسترسی به متادیتا، فقط فایل `database/oracle/cal2/verification/CAL2-R2B2-CONTRACT-VERIFY-READONLY.sql` را با `F5` اجرا کنید. خروجی مورد انتظار `CAL2_R2B2_READONLY_CONTRACT_PASS` است. این فایل فقط SELECT دارد.
2. از ریشه سورس `node tools/verify-cal2-personal-r2b2.mjs` را اجرا کنید؛ خروجی مورد انتظار `CAL2_R2B2_STATIC_VERIFY_PASS` است.
3. Build واقعی Java و Angular را در محیط دارای Maven/Node dependencies اجرا کنید؛ در محیط تهیه Patch، Maven Wrapper به مخزن Maven دسترسی نداشت.
4. حالت آزمایشی را با متغیر بالا فعال کنید و موارد زیر را **فقط در محیط آزمایشی** تست کنید.

## ماتریس UAT

| شناسه | آزمون | انتظار |
|---|---|---|
| T01 | ثبت یادداشت بدون یادآوری | Entry و یک Occurrence ساخته شود؛ Alert ساخته نشود |
| T02 | ثبت یادداشت با یادآوری امروز ساعت ۰۹ | Alert سرور در زمان مقرر AVAILABLE شود |
| T03 | ثبت TASK با سه روز پیش‌آگاهی روزانه | چهار Alert مجزا: روزهای -۳/-۲/-۱ و روز موعد |
| T04 | حالت «یک بار» قبل از موعد | یک ADVANCE و یک AT_DUE؛ نه هرروز |
| T05 | انتخاب تقویم شمسی و تکرار ماهانه | Occurrence ماه بعد مطابق CALENDAR_DATE و روز تعیین‌شده |
| T06 | روز نامعتبر در ماه کوتاه (هر دو سیاست) | SKIP نوبتی نمی‌سازد؛ LAST_DAY آخرین روز واقعی را برمی‌گزیند |
| T07 | تکرار هفتگی | ماسک ISO مستقل از شروع هفته در نمای شمسی |
| T08 | Acknowledge یک پیام | فقط همان Alert ACK شود؛ اعلان روز بعد محفوظ بماند |
| T09 | Snooze پانزده‌دقیقه‌ای | PLANNED_AT_UTC ثابت؛ NEXT_ELIGIBLE_AT_UTC تغییر کند؛ پیام بعداً دوباره ظاهر شود |
| T10 | DONE کردن یک وقوع TASK | فقط همان Occurrence به DONE برود؛ اعلان‌های باز همان وقوع لغو شوند |
| T11 | Update با ETag کهنه یا بدون If-Match | به‌ترتیب 412 / 428 و بدون تغییر رکورد |
| T12 | حذف | Soft Cancel، رکوردها و سوابق باقی بمانند؛ مورد از ماهانه مخفی شود |
| T13 | ارسال دوباره POST با Idempotency-Key یکسان | همان Entry؛ با Payload متفاوت 409 |
| T14 | خاموشی مرورگر در زمان موعد | Scheduler سروری Alert را در Oracle AVAILABLE کند؛ پس از باز کردن UI دیده شود |
| T15 | قطع و وصل Backend | اعلان‌های قدیمیِ پیش‌آگاهی باعث سیل پیام نشوند؛ سابقه حفظ شود |
| T16 | غیرفعال‌بودن Demo بدون Principal | HTTP 401؛ بدون هویت جعلی از Query/Body |
| T17 | آزمون مجدد تقویم رسمی/کاری | فرم‌ها، رویدادهای رسمی، تعطیلات و Resolution بدون تغییر |

## محدودیت‌های صریح این نسخه

- این Patch مرحله **R2-B2 Pilot** است، نه پیاده‌سازی نهایی همه نیازمندی‌های R2-A2. تغییر وقوع منفرد، `THIS_AND_FUTURE`، `SPLIT_SERIES`، ویرایش Rule سری و Audit Provider مشترک هنوز تکمیل نشده‌اند؛ در رابط کاربری ویرایش سری غیرفعال است.
- برای تکرار، پشتیبانی از ماه شماره ۱۳ و گزینه‌های Nth Weekday و COUNT_LIMIT/UNTIL در این رابط وجود ندارد. برای استفاده بانکی باید سناریوهای DST، تغییر TZDB، Coverage تقویم، حجم زیاد و چندنمونه‌ای Scheduler آزمایش شوند.
- `@Scheduled` افق ۹۰ روزی را بازسازی می‌کند؛ سیاست نگهداری Idempotency/Alert و عملکرد بار سنگین هنوز تصویب نشده‌اند.
- در نسخه اولیه، بازگشایی وقوع DONE به معنی احیای خودکار اعلان‌های لغوشده نیست؛ کاربر باید برای موعد جدید سیاست تازه ثبت کند (در فاز تکمیلی).
- بازگرداندن اعلان‌های مربوط به تاریخ‌های پیش‌آگاهی بسیار قدیمی ممنوع است؛ کد بیش از ۲۴ ساعت تأخیر را برای پیش‌آگاهی‌ها `EXPIRED` می‌کند. این عدد یک **سیاست آزمایشی** است و نیازمند تصمیم کسب‌وکار است.
- اجرای SQL روی Oracle کاربر و Integration Test واقعی انجام نشده است. هیچ وعده‌ای درباره بی‌خطا بودن Runtime بدون این آزمون‌ها داده نمی‌شود.
