# FEE UX R3-B — کنترل یکپارچگی مرحله اخذ کارمزد

## دامنه

این Patch تنها در FEE (اسکیما و API فعلی FEE) تغییر ایجاد می‌کند. موتور مستقل FEE2، ماژول Product Builder، منوی اصلی، Oracle DDL و Seed بدون تغییر می‌مانند. پیش‌نیاز: R2.3 و R3-A نصب شده باشند.

در R3-A فرم «مراحل اخذ» فقط خواندنی بود. در R3-B پس از انتخاب تعریف و نسخه کارمزد، فرم ثبت/ویرایش مرحله فعال می‌شود. قاعده محاسبه و مؤلفه اختیاری فقط از همان نسخه پیشنهاد می‌شوند و Backend *برای همه درخواست‌های Create/Update به API عمومی FEE* تطابق را بررسی می‌کند، حتی اگر درخواست از فرم فنی قدیمی باشد.

## اعتبارسنجی سمت سرور

- شناسه‌های نسخه و قاعده اجباری، مثبت و صحیح هستند؛ شناسه مؤلفه در صورت ارائه باید مثبت و صحیح باشد.
- زمان ثبت و ویرایش مرحله، نسخه قاعده محاسبه باید با `FEE_CHARGE_STAGE.FEE_DEFINITION_VERSION_ID` برابر باشد.
- در صورت تعیین `CHARGE_COMPONENT_ID`، مؤلفه نیز باید به همان نسخه تعلق داشته باشد.
- در ویرایش جزئی، فیلدهای حذف‌شده از درخواست از رکورد قفل‌شده فعلی خوانده می‌شوند؛ ارسال صریح مقدار Null برای کلید اجباری مجاز نیست.
- جابه‌جایی نسخه یک `FEE_CALCULATION_RULE` یا `FEE_CHARGE_COMPONENT` که مرحله اخذ به آن وابسته است، ممنوع است.
- در تراکنش، ردیف مرحله و والدهای مربوطه با `FOR UPDATE` قفل می‌شوند تا رقابت هم‌زمان موجب عبور از کنترل نشود.
- موارد نامعتبر با خطای HTTP 422 و پیام فارسی قابل مشاهده در فرم برمی‌گردند.

**محدودیت:** این اعتبارسنجی در API پروژه اعمال می‌شود؛ تغییر مستقیم SQL خارج از API همچنان می‌تواند از این کنترل عبور کند. برای جلوگیری در سطح پایگاه داده باید قید/Trigger مستقل در آینده بررسی شود؛ در R3-B هیچ DDL جدیدی اجرا نمی‌شود.

## نصب مستقل روی Windows

1. از پروژه و خصوصاً فایل‌های FEE نسخه پشتیبان تهیه کنید. برنامه را متوقف کنید.
2. ZIP را در `D:\Projects\core-banking-prototype-v0` استخراج کنید. ابزار و مستندات داخل `tools` و `docs` هستند؛ فایل زائدی در Root اضافه نکنید.
3. اجرا کنید:

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\install-fee-r3b.mjs --check
node tools\install-fee-r3b.mjs
node tools\verify-fee-r3b.mjs
node tools\verify-fee-r3a.mjs
node tools\verify-fee-ux-r23.mjs
node tools\verify-fee2-studio.mjs
node tools\verify-pdl-r29-finalization.mjs
build-production.cmd
```

4. بعد از Build موفق، برنامه را راه‌اندازی و مرورگر را با `Ctrl+Shift+R` تازه کنید.
5. نشانی: `http://localhost:8091/#/fee/workspaces/collection`

## آزمون پذیرش (UAT)

- یک تعریف و نسخه‌ای که قاعده محاسبه دارد انتخاب کنید. تب «مراحل اخذ» باید دکمه «افزودن مرحله» نشان دهد. در نسخه بدون قاعده معتبر، راهنمای رفتن به طراحی قواعد نمایش داده می‌شود.
- در فرم مرحله، بازکردن انتخابگر قاعده محاسبه باید فقط قواعد همان نسخه را نشان دهد. مؤلفه اختیاری نیز همین شرط را دارد.
- تغییر نسخه در فرم فنی باید انتخاب قاعده و مؤلفه قبلی را پاک و فهرست آنها را دوباره محدود کند.
- با استفاده از داده‌های آزمایشیِ غیر تعرفه‌ای و پس از تهیه Backup، ثبت صحیح را با نسخه و قاعده متعلق به آن آزمایش کنید.
- تست منفی: از API `/api/v1/fees/admin/tables/FEE_CHARGE_STAGE/rows` شناسه قاعده از نسخه متفاوت ارسال شود. باید 422 دریافت شود و هیچ رکورد جدیدی ساخته نشود. این آزمون را فقط در محیط UAT انجام دهید.
- تست منفی ویرایش: تلاش برای انتقال یک قاعده یا مؤلفه دارای مرحله به نسخه دیگر باید 422 برگرداند.
- صحت فیلتر چهار تب دیگر و حفظ ناوبری R22.1/FEE2/محصول‌ساز کنترل شود.

## بازگشت

```bat
node tools\uninstall-fee-r3b.mjs --check
node tools\uninstall-fee-r3b.mjs
build-production.cmd
```

**هشدار:** پس از بازگشت، در نسخه R3-A فرم مرحله اخذ در استودیو دوباره فقط خواندنی خواهد بود و کنترل‌های Backend جدید حذف می‌شوند. برای ایمنی، بهتر است در محیطی که داده‌های واقعی ثبت می‌کند R3-B را بدون جایگزین DB-level حذف نکنید. ابزار Uninstall فقط سورس را برمی‌گرداند و داده Oracle را تغییر نمی‌دهد.

## وضعیت آزمون‌ها

آزمون‌های ثابت و سیاست Java اجرا شده‌اند؛ کامپایل کامل Angular/Java و آزمون متصل به Oracle باید با دستور `build-production.cmd` و UAT واقعی تأیید شوند.
