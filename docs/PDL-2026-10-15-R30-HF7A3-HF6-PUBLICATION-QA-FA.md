# گزارش فنی و چک‌لیست تحویل R30-HF7-A3/HF6

**موضوع:** اتصال ممیزی سه قرارداد سلسله‌مراتبی به تصمیم واقعی تصویب نسخه (`canApprove`)  
**مبنا:** `R30-HF7A3-HF5-HF1` — Build کامل، ۱۸۴ آزمون JUnit با صفر شکست و اجرای Spring Boot در ویندوز، مطابق لاگ دریافتی ۱۴۰۵/۰۷/۲۳ (۲۰۲۶-۱۰-۱۵).  
**نوع بسته:** اصلاح کد و آزمون؛ **بدون DDL/DML، بدون تغییر Oracle، بدون فعال‌سازی Runtime.**

## مسئله و اقدام

در مبنای HF5، متد خواندنی `ProductRuleHierarchyAudit.audit(...)` سه رابطه والد/فرزند را بررسی می‌کرد، اما `ProductRuleGovernanceService.report(...)` فقط نتیجه ممیزی `DEPOSIT_PRODUCT_TERM_RULE` و `PRODUCT_PRICING_RULE` را وارد وضعیت حاکمیت نسخه می‌کرد. ازاین‌رو وجود فرزند ناسازگار ممکن بود مانع تصویب طراحی نسخه نشود.

HF6 در گزارش واقعی برای کنترل‌های زیر (در صورت شمول دامنه و فعال بودن ماژول) از همان ممیزی خواندنی استفاده می‌کند:

| کنترل مادر | فرزند/فرزندان بررسی‌شده | کنترل‌ها |
| --- | --- | --- |
| `PRODUCT_CHANNEL_RULE` | `PRODUCT_CHANNEL_OPERATION` | شناسه رابطه، وضعیت/تاریخ معتبر، معنای عملیات، عدم مجازشدن عملیات در کانال ممنوع |
| `PRODUCT_ELIGIBILITY_RULE` (فقط تسهیلات) | `LOAN_ELIGIBILITY_EXTENSION` | شناسه رابطه، پرچم‌ها، تعداد صحیح ضامن، وضعیت/تاریخ معتبر |
| `DEPOSIT_PRODUCT_CLOSURE_RULE` (فقط سپرده) | `DEPOSIT_PRODUCT_CLOSURE_PRECHECK`، `DEPOSIT_PRODUCT_CLOSURE_SETTLEMENT_RULE`، `DEPOSIT_PRODUCT_CLOSURE_APPROVAL_RULE` | شناسه رابطه، ترتیب مثبت، الزام‌ها، مقصد سازگار با روش تسویه، وضعیت/تاریخ معتبر |

شکاف فرزند در همان ردیف مادر با وضعیت `INVALID_SEMANTICS` و توضیح کسب‌وکاری منعکس شده، وارد `blockers` می‌شود و `canApprove=false` ایجاد می‌کند. شکست واکشی کامل فرزند نیز **Fail Closed** است. نبود فرزند برای خانواده‌های واقعاً اختیاری، به معنی وجود مجوز اجرایی نیست.

**مرز ایمنی:** `canOpen` سپرده و تسهیلات مانند نسخه پایه بسته باقی مانده است. این Patch هیچ مجوز افتتاح، اعطا، پرداخت، برداشت یا وصول اضافه نمی‌کند. لایه تعیین تقدم/حل تعارض دامنه‌های کانال، عملیات، مشتری، مبلغ و سیاست بانک هنوز موتور Runtime تأییدشده ندارد.

## تغییرات کد

- `ProductRuleGovernanceService.java`: فراخوانی ممیزی سه خانواده در `report`، جمع‌کردن تعداد نقص‌ها و نمایش دلیل در `EffectiveRule` و `blockers`.
- `ProductRuleHierarchyHF7A3HF6Test.java`: ۱۲ سناریوی JUnit (با Repository موک)، از جمله مجوز متعارض، FK اشتباه، وضعیت نامعتبر، شکست Oracle read، بازه آینده، اهلیت تسهیلات، کنترل/تسویه/تأیید خاتمه و محافظ‌های عملیاتی.
- `ProductRuleGovernanceFixture.java` و چهار آزمون تاریخی: افزودن شناسه‌های واقعی مدل به نمونه والد و اعلام صریح عدم وجود **فرزندان اختیاری** در سناریوهای قدیمی؛ هیچ آزمونی حذف یا Disable نشده است.
- Verifierهای HF7-A1، HF7-A2 و HF4: به‌روزرسانی فقط Repository آزمایشی تا فرزند خیالی نسازند؛ منطق اصلی آزمون‌ها بدون تضعیف باقی است.
- `verify-pdl-r30-hf7a3-hf6-publication.mjs`: اجرای Java واقعی با Repository خواندنی و کامپایل کلاس JUnit با امضاهای سبک چارچوب آزمون (جایگزین Maven نیست).
- `build-production.cmd` و `.sh`: افزودن Verifier جدید به زنجیره ساخت.

## دستور نصب روی Baseline درست

Patch فقط برای نسخه تأییدشده `R30-HF7A3-HF5-HF1` تهیه شده است. از کل پروژه پشتیبان بگیرید. محتوای ZIP کوچک را در ریشه `D:\Projects\core-banking-prototype-v0` با حفظ ساختار پوشه‌ها استخراج و فایل‌های هم‌نام را جایگزین کنید.

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\verify-pdl-r30-hf7a3-hf6-publication.mjs
node tools\verify-pdl-r30-hf7a1-semantic.mjs
node tools\verify-pdl-r30-hf7a2-temporal.mjs
node tools\verify-pdl-r30-hf7a3-hf5-compat.mjs
node tools\verify-release-layout.mjs
build-production.cmd
```

اگر روی نسخه قدیمی‌تر از HF5-HF1 هستید، Patch کوچک را نصب نکنید؛ نسخه کامل HF6 را در یک پوشه جداگانه بررسی کنید.

## چک‌لیست UAT در **محیط آزمون مجاز**

- [ ] Build کامل بدون خطا؛ عدد JUnit قبلی ۱۸۴ و تعداد آزمون‌های افزوده HF6 نیز در گزارش Surefire دیده شود.
- [ ] گزارش نسخه سپرده با کنترل معتبر و بدون فرزند اختیاری: `canApprove=true` مشروط به صحت سایر کنترل‌ها، `canOpen=false`.
- [ ] عملیات مجاز زیر کانال ممنوع: ردیف «کانال و عملیات» `INVALID_SEMANTICS` و تصویب رد شود.
- [ ] فرزند عملیات دارای FK اشتباه/وضعیت نامعتبر/تاریخ مؤثر آینده و مغایرت معنایی: تصویب رد شود.
- [ ] خطای بازیابی فرزند از Repository: خطای واضح در گزارش و رد تصویب؛ نبود شاهد به معنی پذیرش نباشد.
- [ ] فرزند «اهلیت تسهیلات» با تعداد ضامن کسری یا پرچم نامعتبر: تصویب طراحی رد شود.
- [ ] فرزند معتبر اهلیت یا نبود فرزند اختیاری: `canApprove` صرفاً بر اساس کنترل‌های دیگر تصمیم بگیرد؛ اعطای عملیاتی همچنان بسته بماند.
- [ ] قواعد «کنترل پیش از خاتمه»، «تسویه» و «تأیید خاتمه» در صورت عدد ترتیب نامعتبر رد شوند.
- [ ] روش تسویه `DEDUCT` و مقصد پرشده رد شود؛ همان روش بدون مقصد قابل قبول باشد.
- [ ] تصمیم تصویب نسخه از گزارش واقعی Governance استفاده کند و خطای واضح داشته باشد.
- [ ] هیچ داده قدیمی اصلاح/پاک نشود؛ FEE، FEE2، CAL/CAL2، ORG، CIF و DPS2 تغییر رفتاری ناخواسته نداشته باشند.

## محدودیت‌ها و گام بعد

HF6 سه رابطه را در **حاکمیت طراحی** متصل می‌کند؛ نه موتور اجرایی/تراکنشی. **ممیزی همه ۵۴ جدول فیزیکی PDL و اتصال Runtime هنوز کامل نیست.** پس از تأیید کامل Build و UAT خواندنی، اولویت بعدی تکمیل پوشش باقی روابط و سپس یکپارچه‌سازی واقعی مصرف نسخه مصوب در HF7-B/HF7-C خواهد بود. هرگونه رفع محافظ `canOpen` مستلزم شواهد مستقل عملیاتی است.
