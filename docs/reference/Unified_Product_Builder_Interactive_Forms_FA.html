اعتبارسنجی قواعد تخصصیSPECIALIZED_REQUIREMENTSبرای هر ماژول تخصصی فعال، حداقل رکورد اصلی و فیلدهای الزامی کنترل می‌شود؛ در صورت نقص، «مرحله بعد» متوقف و Tab/فرم دارای خطا مشخص می‌شود.
مدت‌های مجاز سپردهTERM_UNIT_CODE / TERM_VALUE / TERM_CODEکاربر ابتدا واحد و سپس مقدار مدت را وارد می‌کند؛ TERM_CODE به‌صورت سیستمی از این دو مقدار تولید می‌شود.
راهنمای فرم‌هاField Hintمثال‌ها، مقادیر فنی و توضیحات آموزشی از عنوان فیلد جدا شده و به Hint زیر کنترل منتقل می‌شوند تا فرم عملیاتی خلوت و یکدست بماند.

جنسیت مشتریGENDER_CODEفقط برای شخص حقیقی کاربرد دارد؛ در حالت «فقط شخص حقوقی» کنترل غیرفعال و مقدار آن از قاعده اهلیت حذف می‌شود.
یکتایی قاعده کانالPRODUCT_VERSION_ID + CHANNEL_CODEبرای هر نسخه محصول، هر کانال فقط یک قاعده کانال دارد. UI انتخاب تکراری را مسدود می‌کند و Backend/Database نیز باید همین یکتایی را enforce کند.
یکتایی محدوده سازمانیPRODUCT_VERSION_ID + ORG_UNIT_IDهر واحد سازمانی در هر نسخه محصول فقط یک رکورد محدوده دارد.
یکتایی مدارک و استعلام‌هاDocument+Stage / Inquiry+Stageدر UI محصول‌ساز، تکرار همان مدرک یا استعلام در همان مرحله مسدود می‌شود. گام داخلی فرایند توسط Workflow / State Machine مدیریت می‌شود و در فرم کاربر نمایش داده یا از کاربر دریافت نمی‌شود.
یکتایی قواعد تخصصی سپردهTransaction / Term / Hold / Closure keysنوع تراکنش، مدت مجاز، نوع مسدودی، نوع بستن و اجزای وابسته به بستن بر اساس کلید کسب‌وکاری خود یکتا کنترل می‌شوند.
یکتایی وثیقه تسهیلاتPRODUCT_VERSION_ID + LOAN_PRODUCT_COLLATERAL_IDبرای هر نوع وثیقه در یک نسخه فقط یک قاعده وثیقه قابل تعریف است.
اصل جلوگیری از DuplicateBusiness Unique Keyبرای جداول تکرارشونده، پس از ثبت یک مقدار یکتا، آن مقدار از ComboBox / Multi-Select رکوردهای بعدی حذف می‌شود. با حذف رکورد، گزینه دوباره در فهرست قابل انتخاب ظاهر می‌شود. کنترل Duplicate در «مرحله بعد» و «بازبینی نهایی» نیز باقی است و همین Unique Keyها باید در Backend/Database enforce شوند.
نمایش جداول چندرکوردیRepeatable Gridتمام بخش‌هایی که امکان ثبت چند رکورد دارند در Wizard به‌صورت Grid نمایش داده می‌شوند. هر ردیف دارای عملیات «مشاهده»، «اصلاح» و «حذف» است؛ فرم کامل رکورد فقط هنگام افزودن یا اصلاح باز می‌شود.
اصلاح تراکنشی رکورد GridEdit → Commit / Cancelبا انتخاب «اصلاح»، یک Snapshot از آخرین مقدار ثبت‌شده نگهداری می‌شود. تغییرات فرم تا زمان انتخاب «ثبت تغییرات و بستن» در Grid، Payload، کنترل یکتایی و ذخیره پیش‌نویس اعمال نمی‌شوند. «انصراف» رکورد را دقیقاً به Snapshot قبلی برمی‌گرداند.
نمایش مبالغMonetary Fieldsتمام فیلدهای مبلغ، مانده و درآمد هنگام ورود با جداکننده هزارگان نمایش داده می‌شوند؛ مقدار ارسالی به Backend بدون Comma و به‌صورت عدد خام نگهداری می‌شود.
مدت‌های مجاز سپردهTERM applicabilityبرای حساب جاری و قرض‌الحسنه پس‌انداز، ماژول مدت/سررسید غیرقابل اعمال است و هیچ رکورد Allowed Term صادر نمی‌شود. برای سپرده مدت‌دار/گواهی سپرده، چند گزینه مستقل مانند ۳، ۶ و ۱۲ ماه قابل تعریف است.
نمای ۳۶۰ محصولOperational Product Controlفرم مجزای پس از ثبت محصول برای کنترل وضعیت محصول و نسخه، مجاز بودن افتتاح/اعطا، خدمت‌رسانی، کانال‌ها، محدوده سازمانی، ماژول‌ها و آمادگی عملیاتی. این فرم وضعیت موازی ایجاد نمی‌کند و روی جداول موجود Product Builder نگاشت می‌شود.
ارتباط محصولاتPRODUCT_RELATIONSHIPدر UI هیچ شناسه عددی از PRODUCT_ID یا PRODUCT_VERSION_ID از کاربر دریافت نمی‌شود. مبدأ از محصول جاری تعیین می‌شود و «محصول مقصد» فقط از کاتالوگ محصولات قابل انتخاب است و ورود/ویرایش دستی ندارد؛ نسخه مقصد فقط در صورت نیاز قابل انتخاب است. شناسه‌های فنی صرفاً در Backend نگهداری می‌شوند.
کنترل بازه حداقل/حداکثرMIN_* / MAX_* + Date Rangesدر تمام فرم‌های محصول‌ساز، هر زوج حداقل/حداکثر باید شرط حداقل ≤ حداکثر را رعایت کند؛ از جمله مبلغ رابطه، سن/سابقه، مبلغ و نرخ قیمت‌گذاری، پله نرخ، مبلغ افتتاح و تراکنش، مسدودی، تعداد مالکان، مبلغ/سهم تسهیلات، مدت و اقساط بازپرداخت، پوشش وثیقه و محدوده‌های مرجع. همچنین تاریخ شروع نباید بعد از تاریخ پایان باشد. UI در زمان ورود و هنگام ثبت/مرحله بعد این قاعده را کنترل می‌کند.
ثبت رکورد جدید در گریدDraft → Commitدکمه «افزودن رکورد جدید» ابتدا فقط فرم ورود اطلاعات را باز می‌کند. رکورد تنها پس از فشردن «ثبت رکورد» و عبور از کنترل فیلدهای الزامی/یکتایی به گرید اضافه می‌شود؛ «انصراف» هیچ رکوردی ایجاد نمی‌کند.
نسخه مبدأPRODUCT_VERSION.SOURCE_VERSION_IDکاربر شناسه نسخه را وارد نمی‌کند؛ نسخه مبدأ فقط از ComboBox نسخه‌های ثبت‌شده همان محصول انتخاب می‌شود. گزینه خالی به معنی ایجاد نسخه مستقل است.
عملیات مجاز کانالPRODUCT_CHANNEL_OPERATION.OPERATION_CODEاقلام Multi-Select بر اساس دامنه و خانواده/نوع محصول فیلتر می‌شوند. کاربر می‌تواند چند عملیات مرتبط را هم‌زمان انتخاب کند؛ در زمان ثبت، برای هر عملیات یک رکورد مستقل PRODUCT_CHANNEL_OPERATION ایجاد می‌شود تا مدل داده نرمال باقی بماند.
گام داخلی فرایندPRODUCT_REQUIRED_DOCUMENT.PROCESS_STEP_NOاین قلم متعلق به Workflow / State Machine است و در واسط کاربری محصول‌ساز نمایش داده نمی‌شود. مقدار آن باید در لایه فرایند/Backend مدیریت شود و از Payload ورودی کاربر نیز حذف شده است.
داده مرجعLOAN_TYPE / PLAN_TYPE / ...مقادیر قابل انتخاب از فرم‌های مرجع تأمین می‌شوند.
فیلدهای مرجع تسهیلاتLOAN_TYPE / LOAN_USAGE / PLAN_TYPE / ECONOMIC_SUB_SECTION / ...در فرم عملیاتی نام قابل فهم نمایش داده می‌شود؛ شناسه و کد مرجع در پشت صحنه ذخیره می‌شود.
شناسه‌های ارتباطی نسخهPRODUCT_VERSION_IDدر تمام فرم‌های Wizard سیستمی و فقط‌نمایشی است و کاربر امکان تغییر آن را ندارد.
نکته پیاده‌سازی: در نسخه عملیاتی، Selectهای کد و FK باید از API داده مرجع پر شوند. IDها، Audit Fieldها و RECORD_VERSION توسط Backend مدیریت شوند. برای «مدت اعتبار نتیجه استعلام» کاربر مقدار و واحد را انتخاب می‌کند و UI آن را به دقیقه تبدیل کرده و در MAX_RESULT_AGE_MINUTES ذخیره می‌کند. در Multi-Select عملیات کانال، مقدار «نیاز به احراز هویت تکمیلی» در ثبت اولیه روی همه عملیات انتخاب‌شده اعمال می‌شود و پس از ایجاد رکوردهای مستقل، هر عملیات به‌صورت جداگانه قابل اصلاح است. نسخه مبدأ باید در Backend نیز متعلق به همان محصول جاری اعتبارسنجی شود. اقلام عملیات کانال باید در Production از Reference/Application Configuration خوانده و بر اساس خانواده محصول اعتبارسنجی شوند. برای فیلدهای چندانتخابی اهلیت، Prototype مقادیر انتخاب‌شده را به‌صورت چندکدی نگهداری می‌کند؛ در نسخه Production بهتر است API این انتخاب‌ها را به رکوردهای نرمال‌شده/جدول واسط نگاشت کند.
