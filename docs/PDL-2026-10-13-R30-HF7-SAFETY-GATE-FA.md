# R30-HF7-SG — محافظ موقت ایمنی انتشار عملیاتی سپرده و تسهیلات

## محدوده واقعی این نسخه

این Patch **محافظ فوری** است، نه تکمیل HF7-A/B/C و نه گواهی آماده بودن محصول‌ساز برای بانکداری عملیاتی. فقط یک شکاف مثبت کاذب در `canOpen` حوزه تسهیلات را می‌بندد.

- برای محصولات LOAN، `canOpen=false` تا زمانی که موتور عملیاتی و اجرای سیاست‌های مصوب در مسیر درخواست/اعتبارسنجی/اعطا/پرداخت/بازپرداخت/وصول به طور مستند و E2E احراز شوند.
- `canApprove` را دست‌کاری نمی‌کند، زیرا تأیید طراحی با مجوز اعطای عملیاتی تفاوت دارد؛ **ولی هنوز ارزیابی جامع معنایی برای تأیید طراحی موجود نیست.**
- منطق موجود توقف افتتاح محصولات سپرده تا اثبات اتصال Runtime دست‌نخورده می‌ماند.
- کدگذاری HF5، پروفایل سیستمی HF6، و کدگذاری تسهیلات تغییر نمی‌کند.
- هیچ Migration یا DML یا تغییر داده تاریخی ندارد.

## محدودیت‌های مهم و اقدام بعدی

1. نبود پوشش کامل معنایی قواعد افتتاح، تراکنش، ابزار برداشت، مالکیت مشترک، راکدی، مسدودی و خاتمه سپرده؛ همچنین عقد، اهلیت، مالی، بازپرداخت، وثایق و فرایند تسهیلات.
2. فیلدهای NULL تا تعیین حالت معنایی صریح (UNSPECIFIED / BOUNDED / NO_PRODUCT_LIMIT_APPROVED / NOT_APPLICABLE) هنوز قابل ذخیره‌اند.
3. `canApprove` تضمین کامل‌بودن قواعد نیست. تا تکمیل ممیزی و قرارداد مصوب نباید آن را گواهی آمادگی بانکی تلقی کرد.
4. اجرای قطعی Rule پیش از Commit و پوشش کانال‌های شعبه/اینترنت/همراه بانک هنوز آزمون نشده است.
5. محصول‌ها و قراردادهای موجود نیازمند ارزیابی اثر و Cutover مدیریت‌شده‌اند؛ تغییرات جدید نباید خودکار حقوق مشتری را محدود کنند.

## آزمون

`node tools/verify-pdl-r30-hf7-safety-gate.mjs`

آزمون Java جدید به `ProductRuleGovernanceR19Test` افزوده شده است. بررسی Static جایگزین Build کامل Maven یا UAT Oracle نیست.

## معیار پذیرش مرحله بعد

ساخت ماتریس فیلد-به-فیلد برای تمام قواعد هر دو دامنه، کنترل حالت مقدار NULL، تشخیص تعارض و فقدان پوشش، اتصال اجرایی با شواهد واقعی و آزمون E2E. تا آن زمان از ادعای «آماده بهره‌برداری» پرهیز شود.
