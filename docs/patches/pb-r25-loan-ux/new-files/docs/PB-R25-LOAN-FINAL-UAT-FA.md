# PB-R25 — یکپارچه‌سازی فرم‌های تخصصی تسهیلات و آمادگی UAT

**نسخه مبنا:** `core-banking-prototype-v0-2026-10-10-1904.zip` (با R24 و HF1)

**دامنه:** تنها Product Builder/PDL و پیوند اطلاعات پایه تسهیلات؛ بدون DDL، Seed و تغییر رکوردهای موجود Oracle. فایل‌های CIF/DPS/FEE2 دست‌نخورده‌اند. نام‌گذاری رابط کاربری طبق قرارداد «اطلاعات پایه + دامنه کسب‌وکار» است.

## قراردادهای کسب‌وکار

1. **گرید پروفایل تسهیلات:** شناسه‌های تکنیکی عقد/طرح/مصرف/زیربخش اقتصادی/الگوی طبقه‌بندی برای عملیات CRUD حفظ می‌شوند ولی ستون‌های نمایشی از همان مراجع واقعی PDL عنوان فارسی می‌گیرند. اگر رکورد مرجع خارج از صفحه نخست یا غیرفعال باشد، فقط برای نمایش نام همان رکورد با ID خوانده می‌شود؛ استفاده از آن به‌عنوان انتخاب معتبر جدید مجاز نمی‌شود. هیچ عنوان یا شناسه جعلی استفاده نشده است.
2. **قواعد تخصصی تسهیلات:** عنوان «اهلیت متقاضی» مربوط به قاعده مشترک `PRODUCT_ELIGIBILITY_RULE` است؛ «اعتبارسنجی تکمیلی تسهیلات» فرزندِ وابسته `LOAN_ELIGIBILITY_EXTENSION` آن است. ارجاعات اشتباه به خانواده‌های حساب کارگزار حذف شده‌اند و خانواده محصول به فارسی نمایش داده می‌شود.
3. **افزونه مالی (`LOAN_FINANCIAL_EXTENSION`):** سوئیچ «سهم / آورده مشتری» فقط برای **عقد مشارکت مدنی** فعال است؛ خانواده «مشارکتی» به‌تنهایی کافی نیست (مضاربه مجاز نیست). فرم مقدار درصد ۰ تا ۱۰۰ را نشان می‌دهد و در ستون‌های `MIN_CUSTOMER_CONTRIBUTION`/`MAX_CUSTOMER_CONTRIBUTION` نسبت ۰ تا ۱ نگه می‌دارد: مثال ۲۰٪ ↔ ۰٫۲۰. وقتی خاموش باشد مقادیر اختیاری NULL هستند. داده تاریخی نامعتبر خودکار بازنویسی نمی‌شود؛ دکمه اصلاح صریح فراهم است. اعتبارسنجی در Backend نیز اعمال می‌شود.
4. **قواعد بازپرداخت (`LOAN_PRODUCT_REPAYMENT_RULE`):** واحد روز/ماه پیش از کمینه و بیشینه «مدت تسهیلات» است؛ واحد با داده مرجع DPS کنترل می‌شود. هر چهار مجوز تنفس، پیش‌پرداخت، پیش‌پرداخت جزئی و تسویه زودهنگام به‌صورت سوئیچ با مقدار پیش‌فرض ۰/غیرمجاز ارائه می‌شوند. هیچ انتخاب دستی برای مجازکردن آن‌ها الزامی نیست. جزئیات تنفس در حالت غیرمجاز NULL و پیش‌پرداخت جزئی در حالت غیرمجازبودن پیش‌پرداخت، **۰** ذخیره می‌شود (طبق ستون Oracle NOT NULL).
5. **انواع وثیقه:** `PDL.LOAN_PRODUCT_COLLATERAL` همان جدول مرجع موقت با کد، شرح و وضعیت فعال/غیرفعال است. رابطه نوع وثیقه با نسخه محصول در `PDL.LOAN_PRODUCT_COLLATERAL_RULE` نگه‌داری می‌شود؛ فرم اطلاعات پایه ویژگی‌های تکمیلیِ هنوز نهایی‌نشده را نمی‌خواهد اما رکوردهای قبلی را پاک نمی‌کند. طول **شرح** در DDL فقط `VARCHAR2(20 CHAR)` و کد `VARCHAR2(30 CHAR)` است؛ UI مطابق همین محدودیت طول اعتبارسنجی می‌کند. حالت ARCHIVED تاریخی حفظ می‌شود. کد تکراری در Backend رد می‌شود.
6. **اولویت استفاده از نوع وثیقه:** `PRIORITY_NO = 1` یعنی اولویت اول، `2` دوم، `0` یعنی بدون اولویت معین، دقیقاً برابر با `CK_PCR_PRIORITY (PRIORITY_NO >= 0)`؛ عدد، نوع وثیقه یا مبلغ نیست. قابلیت‌های مربوط به ارزیابی واقعی وثایق هنوز وابسته به راه‌اندازی دامنه مستقل وثایق است.
7. **چیدمان و Theme:** از کنترل‌های Material و متغیرهای Theme مشترک سیستم استفاده شده و ساختار RTL، اسکرول افقی جدول در نمایشگر کوچک، اندازه فیلدها و گروه‌بندی فرم‌ها با الگوی موجود حفظ شده است.

## نصب ادغامی و کنترل غیرمخرب

1. پیش از شروع از پوشه پروژه و پایگاه داده نسخه پشتیبان متناسب با محیط UAT داشته باشید.
2. فقط پوشه‌های داخل ZIP اصلاحیه را روی ریشه سورس جدید استخراج کنید. در ZIP فایل‌های مستقل نصب و Payload موجودند؛ جایگزینی مستقیم سورسِ Product Builder انجام نشود.
3. در CMD ویندوز:

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\repair-pb-r25-loan-ux.mjs --check
node tools\repair-pb-r25-loan-ux.mjs --apply
node tools\repair-pb-r25-loan-ux.mjs --check
node tools\verify-pb-r25-loan-final-ux.mjs
node tools\verify-pb-r24-loan-integrity.mjs
node tools\verify-pb-r24-hf1-family-verifier.mjs
build-production.cmd
```

- نصب `--check` هیچ فایل سورسی را تغییر نمی‌دهد. اجرای `--apply` از فایل‌های دست‌خورده در `docs/patch-backups/pb-r25-loan-ux/<timestamp>/` پشتیبان می‌گیرد.
- نصب مجدد باید `CHANGES=0` دهد. در تعارض با تغییر محلی، کل نصب قبل از بازنویسی متوقف می‌شود و باید ادغام دستی و موردی انجام شود.
- هیچ اجرای DDL یا Script Insert/Update روی Oracle لازم نیست.

## چک‌لیست آزمون عملی روی Windows و Oracle

| آزمون | انتظار |
|---|---|
| ثبت عقد مشارکت مدنی و مضاربه در گروه مشارکتی، هر دو فعال | هر دو در گروه تسهیلات مشارکتی قابل مشاهده‌اند؛ سهم مشتری فقط برای **مشارکت مدنی** قابل فعال‌سازی است |
| تعریف پروفایل با عقد، مصرف، طرح مجاز و الگوی عملیاتی | گرید عنوان فارسی FKهای واقعی را نمایش می‌دهد؛ شناسه‌ها در فرم کاربر نمایش فنی ندارند |
| نمایش رکورد قدیمی با نوع عقد غیرفعال | عنوان واقعی در گرید از رکورد مرجع خوانده می‌شود، اما برای انتخاب جدید مجاز نیست |
| باز کردن «قواعد تخصصی» | «اهلیت متقاضی» و ارتباط مستقل آن با اعتبارسنجی تکمیلی روشن است؛ خانواده فارسی نمایش داده می‌شود |
| عقد مشارکت مدنی، سوئیچ آورده روشن، ۲۰ و ۴۰ درصد | در DB به‌ترتیب ۰٫۲۰ و ۰٫۴۰ ثبت و بعد از بازیابی مجدداً ۲۰٪/۴۰٪ دیده می‌شود |
| عقد مضاربه، سوئیچ آورده | غیرفعال است؛ ذخیره مقدار آورده از طریق API نیز باید رد شود |
| سوئیچ آورده خاموش | فیلدهای اختیاری NULL و بدون الزام ثبت هستند |
| بازپرداخت با چهار مجوز غیرمجاز | بدون درخواست فعال‌سازی ثبت می‌شود؛ مقدار همه مجوزها ۰، جزئیات تنفس NULL |
| پیش‌پرداخت غیرمجاز | پیش‌پرداخت جزئی ۰ می‌ماند؛ خطای Oracle NOT NULL رخ نمی‌دهد |
| ورود واحد مدت روز/ماه پیش از حدود مدت تسهیلات | فهرست فقط با گزینه واقعی مرجع؛ در صورت نبود مرجع، خطا روشن و بدون ساخت کد جعلی |
| ثبت نوع وثیقه جدید با کد، شرح، وضعیت فعال/غیرفعال | در PDL ثبت شده و در فرم قاعده وثیقه به‌عنوان گزینه مجاز قابل انتخاب است |
| تکرار کد وثیقه | Backend با پیام مناسب رد می‌کند |
| نوع وثیقه با شرح بیش از ۲۰ نویسه | فرم باید مانع ذخیره شود؛ DDL نیز محافظ دوم است |
| اولویت وثیقه: ۱، ۲ و ۰ | با معنای مشخص و DDL سازگار هستند |
| فرم‌های سپرده و مشتری و FEE2 | چیدمان، مسیرها و ذخیره‌سازی قبلی باید بدون رگرسیون باقی بمانند |

## نتایج کنترل در محیط تولید اصلاحیه

- `PB_R25_LOAN_UX_STATIC_PASS=63 FAIL=0`؛ آزمون‌های قبلی R19/R20/R21/R22/R23/R24/HF1 نیز باید بازاجرا شوند.
- `PB_R25_ISOLATED_JAVA_SMOKE_PASS=25` با JDK 21 برای تطبیق عقد مشارکت مدنی، نسبت آورده، اعتبارسنجی بازپرداخت، اولویت وثیقه و ماهیت متقاضی.
- بررسی نحو فایل‌های TypeScript تغییر یافته موفق است؛ **اجرای کامل Angular CLI/Backend Maven/Oracle در این محیط امکان‌پذیر نیست**. نتیجه قطعی ساخت و UAT واقعی در محیط Windows/Oracle شما مشخص می‌شود و نباید با آزمون ایستا اشتباه گرفته شود.
