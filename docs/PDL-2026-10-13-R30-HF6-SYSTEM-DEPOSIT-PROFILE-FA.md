# R30-HF6 — ایجاد خودکار پروفایل سپرده، فقط‌خواندنی

تاریخ: ۲۰۲۶-۱۰-۱۳ | دامنه: PDL Product Builder | مبنا: سورس تجمیعی R30-HF5

## تصمیم کسب‌وکاری

در فرم `PDL.DEPOSIT_PRODUCT_PROFILE` دو مقدار کسب‌وکاری `DEPOSIT_GROUP_CODE` و `DEPOSIT_TYPE_CODE` وجود دارد. هر دو قبلاً از خانواده محصول تعیین می‌شدند و ورودی واقعی کاربر نبودند. در HF6، **همزمان با ایجاد نسخه محصول سپرده**، Backend این دو مقدار را مطابق خانواده محصول تعیین و رکورد پروفایل را به‌صورت سیستمی ثبت می‌کند. فرم پروفایل اکنون فقط نمایشگر دو مقدار ذخیره‌شده است: عملیات «افزودن»، «ویرایش»، «کپی» و «حذف» برای آن وجود ندارد و API عمومی هم هیچ‌کدام را نمی‌پذیرد.

این تغییر فقط برای سپرده‌های معمولی با خانواده‌های پشتیبانی‌شده اجرا می‌شود. **سپرده‌های کارگزاری NOSTRO/VOSTRO** همچنان از `CORRESPONDENT_ACCOUNT_PRODUCT_PROFILE` و گردش کار مستقل خود استفاده می‌کنند. ایجاد نسخه تسهیلاتی و پروفایل تخصصی تسهیلات دست‌نخورده است.

## رفتار تراکنشی

1. در `ProductBuilderService.create("PRODUCT_VERSION",...)` کنترل‌های پیش‌نویس نسخه، مرجع و حاکمیت مانند قبل اجرا می‌شوند.
2. قبل از تخصیص شماره نسخه، رکورد `PDL.PRODUCT` با `FOR UPDATE` قفل می‌شود. ویرایش هویت محصول نیز همان قفل را می‌گیرد تا تغییر همزمان خانواده نتواند پروفایل اشتباه تولید کند.
3. پس از `repository.insert("PRODUCT_VERSION", ...)`، در **همان `@Transactional`**، مشخص می‌شود آیا کلاس `DEPOSIT` و خانواده غیرکارگزاری است.
4. `DepositProfileIdentityPolicy.forFamily` تنها مرجع تبدیل خانواده به گروه/نوع سپرده است؛ دو مقدار در `DEPOSIT_PRODUCT_PROFILE` با `PRODUCT_VERSION_ID` همان نسخه درج می‌شوند. شناسه فنی، تاریخ و شناسه عامل ایجادکننده توسط repository مدیریت می‌شوند.
5. پیش از درج، `PdlReferenceOptionService.validateChangedValues(...)` این دو کد را با گزینه‌های واقعی و مجاز اطلاعات پایه کنترل می‌کند. **مقدار حدسی یا شناسه surrogate جایگزین کد کسب‌وکاری نمی‌شود.** در صورت نقص اطلاعات پایه یا شکست درج، ایجاد نسخه هم Rollback می‌شود.
6. پس از ایجاد نخستین نسخه، تغییر `PRODUCT_FAMILY_CODE` محصول سپرده مسدود است تا گروه/نوع ذخیره‌شده ناهمخوان نشود. انتقال نسخه موجود به `PRODUCT_ID` دیگر نیز مسدود است.

## خانواده‌های پشتیبانی‌شده

| خانواده محصول | گروه ذخیره‌شده | نوع ذخیره‌شده | پیشوند عددی مستقل R30-HF5 |
|---|---|---|---|
| `QARD_SAVINGS` / `SAVINGS` | `QARD_HASAN` | `SAVINGS` | `3510` |
| `CURRENT_ACCOUNT` / `CURRENT` | `CURRENT` | `CURRENT_NO_INTEREST` | `2510` |
| `SHORT_TERM_DEPOSIT` | `SHORT_TERM` | `SHORT_TERM_DEPOSIT` | `4510` |
| `LONG_TERM_DEPOSIT` | `LONG_TERM` | `LONG_TERM_DEPOSIT` | `5510` |
| `CERTIFICATE_OF_DEPOSIT` | `CERTIFICATE` | `CERTIFICATE_OF_DEPOSIT` | `6510` |

دقت کنید که پیشوند صدور کد *در پروفایل ذخیره نمی‌شود*: سیاست صدور R30-HF5 از کد کسب‌وکاری ذخیره‌شده، پیشوند چهاررقمی مصوب را استخراج می‌کند. این Patch **منطق تولید کد و رجیستری R30-HF5 را تغییر نمی‌دهد**.

## نسخه‌های موجود و ایمنی داده

HF6 هیچ نسخه قدیمی یا پروفایل قدیمی را به‌صورت پس‌زمینه تغییر نمی‌دهد. اگر نسخه موجود پروفایل نداشته باشد، در صفحه فقط‌خواندنی پیام «پروفایل این نسخه یافت نشد» نشان داده می‌شود و صدور کد، تا انجام اصلاح کنترل‌شده، همچنان باید مسدود بماند. هرگونه ترمیم داده‌های تاریخی یک فعالیت **جداگانه با مجوز، برنامه و ثبت ممیزی DBA** است؛ این بسته شامل اسکریپت DML اصلاحی نیست.

**Migration جدید ندارد.** پیش‌نیاز پایگاه داده، Migrationهای قبلی (به‌ویژه R30-HF5) طبق رویه استقرار همان نسخه است. نیازی به اجرای مجدد آنها برای HF6 نیست.

## آزمون غیرنوشتنی و پذیرش در ویندوز

پس از تهیه Backup و استخراج Patch روی پروژه R30-HF5:

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\verify-pdl-r30-hf6-auto-deposit-profile.mjs
node tools\verify-pb-r13.mjs
node tools\verify-pdl-r30-deposit-finalization.mjs
node tools\verify-pdl-r30-hf5-deposit-type-code.mjs
build-production.cmd > "%TEMP%\build-r30-hf6.log" 2>&1
echo BUILD_EXIT_CODE=%ERRORLEVEL%
if exist app\BUILD-DIRTY (echo BUILD_NOT_COMPLETE) else (echo BUILD_CLEAN)
```

بعد از موفقیت Build و استقرار JAR جدید، در محیط UAT مجاز:

- یک **محصول سپرده جدید** از خانواده `QARD_SAVINGS` ایجاد و نسخه اول را ثبت کنید؛ بدون مراجعه به فرم پروفایل، گرید آن باید **یک رکورد** با `QARD_HASAN`/`SAVINGS` داشته باشد.
- برای نسخه دوم همان محصول نیز باید **دقیقاً یک** پروفایل مستقل ساخته شود؛ با نسخه قبلی کپی دستی نمی‌شود.
- ایجاد نسخه محصول تسهیلاتی **نباید** پروفایل سپرده بسازد؛ برای NOSTRO/VOSTRO نیز پروفایل معمولی سپرده خودکار نمی‌شود.
- در صورت نبود کد معتبر در مرجع گروه یا نوع سپرده، ایجاد نسخه باید با پیام خطا متوقف شود و نسخه بدون پروفایل ایجاد نگردد.
- API عمومی Create/Update/Delete برای `DEPOSIT_PRODUCT_PROFILE` باید درخواست را رد کند، حتی اگر کسی مستقیماً endpoint را فراخوانی کند.
- تلاش برای تغییر خانواده محصول سپرده دارای نسخه یا جابه‌جایی مالک نسخه باید رد شود.
- سوابق قدیمی تغییر نکنند. برای بازرسی وضعیت نسخه‌های قدیمی از فایل `docs/patches/PDL-R30-HF6-DEPOSIT-PROFILE-READONLY.sql` استفاده کنید.
- صدور کد سپرده همچنان طبق R30-HF5 فقط پس از تصویب، جاری‌شدن و عبور از قواعد حاکمیت و با پیشوند عددی نوع سپرده مجاز است. افتتاح عملیاتی با صدور کد خودبه‌خود باز نمی‌شود.

## آزمون‌های انجام‌شده و محدودیت‌ها

- آزمون سیاست Java و کنترل‌های Static HF6 محلی انجام شدند.
- رگرسیون‌های Product Builder، R29/R30 و HF1 تا HF5 و FEE2 اجرا شدند.
- صحت Build کامل Angular/Maven در ویندوز، تراکنش واقعی Oracle (شامل rollback خطا)، کنترل همزمانی و UAT عملیاتی **هنوز باید توسط تیم اجرا/DBA تأیید شود**.

## بازگشت

برای برگشت سورس، Backup پیش از Patch را بازیابی کنید؛ Schema تغییری نکرده است. با این حال پس از ایجاد نسخه‌های جدید HF6، استفاده از Backend قدیمیِ دارای CRUD آزاد برای پروفایل برخلاف سیاست حاکمیتی HF6 خواهد بود؛ بازگشت به HF5 باید همراه با کنترل دسترسی به endpointهای قدیمی انجام شود، نه بازنویسی پروفایل یا کدهای صادرشده.
