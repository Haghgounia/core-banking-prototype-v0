1. این سند دقیقاً چه مسئله‌ای را حل می‌کند؟

وقتی یک گام از HTML را تست می‌کنید، باید بتوانید بدون حدس پاسخ دهید: «این دکمه چه چیزی را می‌خواند؟ چه رکوردی باید ساخته/تغییر کند؟ در کدام Package XML قرار دارد؟ کلید اتصال رکوردها چیست؟ و بعد از عملیات با چه Query می‌توانم اثر را در دیتابیس پیدا کنم؟» این سند همین مسیر را استاندارد می‌کند.

نکته بسیار مهم: فایل HTML فعلی یک Prototype/Simulator سمت مرورگر است و مستقیماً به Oracle وصل نیست. بنابراین ستون «رفتار فعلی HTML» از روی JavaScript استخراج شده و ستون «اثر دیتابیس» نگاشت منطقی/هدف بر مبنای XML است. در پیاده‌سازی Backend واقعی باید SQL/API دقیق با همین Trace Contract منطبق شود.

5.3 سناریوی تست پیشنهادی

  1. یک حساب جاری را انتخاب کنید و ACCOUNT_NO و ACCOUNT_ID را یادداشت کنید.
  2. عنوان حساب را تغییر دهید؛ انتظار: DEPOSIT_ACCOUNT.ACCOUNT_NAME تغییر کند و History قابل ردیابی باشد.
  3. نوع تماس «موبایل» را انتخاب و شماره معتبر ثبت کنید؛ انتظار: رکورد جدید در DEPOSIT_ACCOUNT_CONTACT.
  4. نسخه محصول را تغییر دهید؛ انتظار: CURRENT_PRODUCT_VERSION_ID تغییر کند، اما OPENED_PRODUCT_VERSION_ID ثابت بماند و رکورد DEPOSIT_ACCOUNT_PRODUCT_HISTORY ساخته شود.
  5. استثناء شرط ثبت کنید؛ انتظار: DEPOSIT_ACCOUNT_CONDITION_OVERRIDE با APPROVAL_REQUEST_ID قابل Trace باشد.
  6. اختیار صاحب امضا اضافه کنید؛ Service باید ابتدا PARTY_ID را به SIGNATORY_ID معتبر Resolve کند و سپس Authority را بسازد.

5.4 Query کنترل پیشنهادی

-- حساب پایه
SELECT ACCOUNT_ID, ACCOUNT_NO, ACCOUNT_STATUS_CODE, OPENED_PRODUCT_VERSION_ID, CURRENT_PRODUCT_VERSION_ID, ORG_UNIT_CODE, ACCOUNT_NAME
FROM DEPOSIT_ACCOUNT
WHERE ACCOUNT_NO = :ACCOUNT_NO;

-- ویژگی‌ها
SELECT * FROM DEPOSIT_ACCOUNT_ATTRIBUTE WHERE ACCOUNT_ID = :ACCOUNT_ID ORDER BY ACCOUNT_ATTRIBUTE_ID DESC;

-- تماس‌ها
SELECT * FROM DEPOSIT_ACCOUNT_CONTACT WHERE ACCOUNT_ID = :ACCOUNT_ID ORDER BY ACCOUNT_CONTACT_ID DESC;

-- تاریخچه نسخه محصول
SELECT * FROM DEPOSIT_ACCOUNT_PRODUCT_HISTORY WHERE ACCOUNT_ID = :ACCOUNT_ID ORDER BY ACCOUNT_PRODUCT_HISTORY_ID DESC;

-- شرط اختصاصی + مرجع تأیید
SELECT c.*, a.TRACKING_NO, a.APPROVAL_STATUS_CODE
FROM DEPOSIT_ACCOUNT_CONDITION_OVERRIDE c
LEFT JOIN DEPOSIT_OPERATION_APPROVAL_REQUEST a ON a.APPROVAL_REQUEST_ID = c.APPROVAL_REQUEST_ID
WHERE c.ACCOUNT_ID = :ACCOUNT_ID
ORDER BY c.ACCOUNT_CONDITION_OVERRIDE_ID DESC;

-- صاحب امضا و اختیارات
SELECT s.SIGNATORY_ID, s.PARTY_ID, s.STATUS_CODE, au.OPERATION_CODE, au.CHANNEL_CODE, au.MAX_AMOUNT
FROM DEPOSIT_ACCOUNT_SIGNATORY s
LEFT JOIN DEPOSIT_ACCOUNT_SIGNATORY_AUTHORITY au ON au.SIGNATORY_ID = s.SIGNATORY_ID
WHERE s.ACCOUNT_ID = :ACCOUNT_ID
ORDER BY s.SIGNATORY_ID, au.SIGNATORY_AUTHORITY_ID;

7. نکات مهمی که از مقایسه HTML و XML به دست می‌آید

موضوعوضعیت فعلیبرداشت Trace
تعداد گام و PackageHTML شامل Dashboard + 17 حوزه عملیاتی است؛ XML Packageهای بیشتری دارد.نگاشت Many-to-Many طبیعی است؛ Screen را با Package یکی نگیرید.
HTML و دیتابیسHTML Simulator است و State را در JavaScript نگه می‌دارد.هر Action باید در Backend با Transaction/Idempotency/Audit واقعی پیاده شود.
Signatory AuthorityUI Party را انتخاب می‌کند.XML Authority بر مبنای SIGNATORY_ID است؛ Resolve/Validation الزامی است.
Service Subscriptionجدول XML وجود دارد.در HTML فعلی Action صریح Subscription/Unsubscription دیده نمی‌شود.
Fee Overrideجدول DEPOSIT_ACCOUNT_FEE_OVERRIDE وجود دارد.Action صریح Account Fee Override در UI فعلی وجود ندارد.
Early TerminationHTML v11 RC و XML v6 RC همسو شدند.فسخ کامل پیش از موعد ابتدا DEPOSIT_ACCOUNT_CLOSURE با CLOSURE_TYPE_CODE=EARLY_TERMINATION و REASON_CODE=TERM_EARLY_TERMINATION ایجاد می‌کند و سپس وضعیت CLOSED ثبت می‌شود. مورد بسته شد.
Activation / ReopenHTML v11 RC مسیرهای مستقیم را حذف کرده است.ACTIVATE فقط با DEPOSIT_ACTIVATION_RUN/CHECK و REOPEN فقط با DEPOSIT_ACCOUNT_REOPENING + Approval اجرا می‌شود. مورد بسته شد.
Balance Ownershipدر Simulator مانده روی Account object است.در XML مالک واقعی مانده Package 17 است و DEPOSIT_ACCOUNT نباید مانده پولی نگه دارد.

8. چک‌لیست جلسه و عیب‌یابی

  1. اول ACCOUNT_NO را به ACCOUNT_ID تبدیل کن.
  2. Action کاربر را مشخص کن: Read / Command / Posting / Reversal.
  3. Package مالک را تعیین کن؛ Cross-Packageها را جدا نام ببر.
  4. رکورد Header را پیدا کن؛ سپس Child/History/Audit را دنبال کن.
  5. اگر پول جابه‌جا شده، حتماً TRANSACTION_ID → LEG → SUBLEDGER → BALANCE را Trace کن.
  6. اگر Approval دارد، APPROVAL_REQUEST_ID و Tracking No را پیدا کن.
  7. اگر درخواست بیرونی است، ORIGIN_REQUEST_REF / CORRELATION_ID / IDEMPOTENCY_KEY را کنترل کن.
  8. اگر Status تغییر کرده، هم Master و هم History/Event را مقایسه کن.
  9. هیچ UI Caption فارسی را با Code داخلی اشتباه نگیر؛ Code در DB/Integration می‌ماند.
  10. در پایان اثر عملیات باید با Query مستقل از UI قابل اثبات باشد.
