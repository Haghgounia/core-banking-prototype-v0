# Product Builder PB-R14 — اصلاح حساب مشترک، مسدودی و خاتمه سپرده

**مبنای تغییر:** بسته PB-R13 و نمونه HTML مرجع `docs/reference/Unified_Product_Builder_Interactive_Forms_FA.html`، بدون تغییر Schema، Migration یا قرارداد API.

## تحلیل علت خطای حساب مشترک

در نسخه همراه پروژه، داده‌های صادراتی `DPS.REF_OWNERSHIP_TYPE_CODE` برای «انفرادی/مشترک» کدهای `1/2` دارند؛ در HTML مرجع Product Builder برای `PDL.DEPOSIT_PRODUCT_JOINT_RULE.OWNERSHIP_TYPE_CODE` کدهای `SINGLE/JOINT` تعریف شده‌اند. مشابه آن، مرجع امضا (`1`,`2`,`3`) و تقسیم سود (`1`,`2`,`3`,`4`) با Enumهای PDL متفاوت است. نسخه قبلی گزینه‌ها را بدون نگاشت دامنه‌ای تقاطع می‌داد و می‌توانست به گزینه خالی/نامعتبر یا ردشدن داده در Oracle منجر شود. **بدون خروجی خطای سرویس و قیود واقعی Oracle، نمی‌توان با قطعیت گفت همین عامل تنها علت پیام «خطای پیش‌بینی‌نشده» کاربر بوده است.**

### رفع خطا

1. نگاشت صریح مقادیر شناخته‌شده DPS به PDL بر اساس مفهوم کسب‌وکار برقرار شده است؛ هنگام ساخت گزینه، **قید CHECK واقعی پایگاه داده PDL تعیین می‌کند کدام CODE مجاز است**. در دیتابیس‌هایی که هنوز کدهای عددی را می‌پذیرند، همان کد عددی ارسال می‌شود. مقدار بدون تطبیق معتبر نمایش داده نمی‌شود.
2. گزینه‌های خاص مرجع مانند «صغیر با ولی/قیم»، «امضای هر دو نفر» یا «مالک اصلی» که معادل یک‌به‌یک تأییدشده‌ای در Enumهای PDL ندارند، **عمداً به گزینه‌ای مشابه اما غیریکسان تبدیل نشده‌اند**. برای پشتیبانی نیازمند تصمیم مالک دامنه و Migration مصوب هستند.
3. کنترل مقادیر «حداقل/حداکثر صاحبان» و «حداقل امضاکنندگان» در Backend قبل از اجرای INSERT/UPDATE انجام می‌شود و پیام فارسی دارد.
4. Frontend اطلاعات `ProblemDetail.detail` را نشان می‌دهد، نه اینکه تمام پاسخ‌های HttpErrorResponse را «خطای پیش‌بینی‌نشده» اعلام کند. خطای ORA-02290 نیز به‌عنوان نقض دامنه مجاز تشخیص داده می‌شود؛ جزئیات فنی محرمانه پایگاه داده در پاسخ افشا نمی‌شود.

## مسدودی و خاتمه سپرده

- `DEPOSIT_PRODUCT_HOLD_RULE.HOLD_TYPE_CODE`: نوع مسدودی از مرجع `dps-hold-types` در صورت سازگاری با CHECK یا از گزینه‌های مجاز خود CHECK خوانده می‌شود؛ کنترل ComboBox در Angular موجود است.
- `DEPOSIT_PRODUCT_CLOSURE_RULE.CLOSURE_TYPE_CODE`: انواع خاتمه؛ `BALANCE_DESTINATION_CODE`: مقصد تسویه مانده؛ `STATUS_CODE`: وضعیت قاعده به‌صورت انتخابی هستند.
- `DEPOSIT_PRODUCT_CLOSURE_SETTLEMENT_RULE.SETTLEMENT_METHOD_CODE` و `DESTINATION_CODE`: روش و مقصد تسویه در فرم فرزند هم همین پوشش را دارند.
- برای مواردی که داده مرجع DPS موجود نیست، فقط کدهایی ارائه می‌شوند که **در CHECK همان ستون در Oracle وجود دارند** و مطابق HTML مرجع عنوان فارسی معتبر دارند؛ این فهرست با عنوان «مقادیر مجاز پایگاه داده محصول» مشخص است. اگر CHECK هم موجود نباشد، گزینه ساخته نمی‌شود و فرم قابل ثبت نخواهد بود.

## وضعیت آزمون

| کنترل | نتیجه |
|---|---|
| Verifier اختصاصی PB-R14، ۲۱ کنترل | PASS (static) |
| Verifier های PB-R11/R12/R13 و ساختار انتشار | PASS (static) |
| کامپایل متد Java نگاشت با JDK 21 و اجرای سناریوهای کد DPS/PDL و فهرست خاتمه/مقصد/وضعیت | PASS (local, isolated stubs; not Spring runtime) |
| کامپایل و اجرای قواعد تعداد مالک و امضاکننده با JDK 21 | PASS (local, isolated stubs) |
| بررسی نحوی فایل TypeScript | PASS (transpile only, not Angular AOT) |
| JUnit روی Maven واقعی، Build تولید، مرورگر، Oracle و ثبت/ویرایش/بازیابی عملی | **NOT TESTED** |

JUnit های جدید داخل پروژه قرار گرفته‌اند و باید در `build-production.cmd` ویندوز اجرا شوند. 

## اقدام پیشنهادی نصب/آزمون

پس از پشتیبان‌گیری و توقف برنامه، Patch را روی **نسخه PB-R13 اجراشده** در مسیر پروژه استخراج کنید. سپس:

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\verify-pb-r14.mjs
build-production.cmd
bin\start
```

فرم حساب مشترک را ابتدا با مالکیت مشترک، الگوی امضای هر یک و توزیع سود مساوی ثبت کنید؛ سپس یک مورد نامعتبر (حداقل مالکان بزرگ‌تر از حداکثر) و وضعیت Clone/Update را آزمایش کنید. فرم‌های مسدودی، خاتمه و زیرمجموعه تسویه خاتمه را باز کنید و وجود گزینه‌های فارسی و Persist/Refresh را کنترل کنید.

برای کنترل Database بدون تغییر اطلاعات، `database/oracle/pdl/diagnostics/pb-r14-joint-hold-closure-readiness.sql` را در SQL Developer اجرا کنید. خروجی این Query برای تأیید قطعی دامنه‌های پذیرفته‌شده توسط پایگاه داده و فعال بودن مرجع‌ها لازم است.

**شرط Release نهایی:** Build واقعی ویندوز، Testهای Maven، تأیید Oracle و آزمون UI/CRUD باید PASS شوند.
