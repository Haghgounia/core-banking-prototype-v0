# ORG — گام R2-A: بستن R1 و بازبینی نسخه تجمیعی مکان و نشانی، فقط‌خواندنی

**تاریخ:** ۲۴ اکتبر ۲۰۲۶  
**وضعیت پایگاه داده:** `R1 BACKFILL COMMITTED / POST-COMMIT VERIFIED` بر پایه خروجی واقعی SQL Developer ارائه‌شده توسط کارفرما.  
**وضعیت برنامه:** `R2-A SOURCE_READY / BROWSER + LIVE API UAT PENDING`.

## ۱. شواهد تأیید R1

کارفرما ابتدا اجرای R1 `02` و `03` با تصمیم Apply را اعلام کرد و سپس `COMMIT` را در نشست مربوط اجرا کرد. اجرای دوباره `04-ORG-UNIT-LOCATIONS-VERIFY-READONLY.sql` پس از COMMIT نتایج زیر را داشت:

| کنترل | مقدار تأییدشده |
|---|---:|
| `LEGACY_BACKFILL_FLAG=1` | 1340 |
| `VERIFIED_ROWS` | 1340 |
| `MISMATCHED_ROWS` | 0 |
| `LEGACY_OU_LOCATION_LINKS` | 1340 |
| `LEGACY_PHYSICAL_LOCATIONS` | 1337 |
| `LEGACY_POSTAL_ADDRESSES` | 1337 |
| `LEGACY_SERVICE_POINTS` | 0 |

با این شواهد، «انتقال اولیه و ماندگاری مقادیر» کامل است؛ ولی «تکمیل مدل، فرم CRUD و بازنشستگی مراجع قدیمی» هنوز تکمیل نشده است.

### مکان مشترک 1327

`LOCATION_ID=1327` عمداً در چهار استقرار مستقل استفاده شده است. با تأیید کارفرما:
- `UNIT_CODE=63529`: «مستقل مرکزی» واحد فیزیکی؛
- `UNIT_CODE=5561`: «حسابداری بستن روزانه متمرکز»، مجازی؛
- `UNIT_CODE=67280`: «فرابانک»، مجازی؛
- `UNIT_CODE=93955`: «بانکداری متمرکز مرتبط با NGFS»، مجازی.

نشانی ساختمان مرکزی **نشانی مرجع** سه واحد مجازی است؛ تکرار `LOCATION_ID` نباید به اشتباه پاک یا تفکیک شود. همچنین هیچ‌یک از رکوردها نباید خودکار به نوع استقرار «فیزیکی» برچسب بخورند؛ تعیین نوع در مدل R2-B باید **مستقل از `LOCATION_ROLE_CODE`** با تصمیم کسب‌وکار انجام گیرد.

## ۲. محدوده تغییر R2-A در سورس

- API جدید فقط‌خواندنی: `GET /api/v1/organization/unit-location-canonical-review` با پارامترهای اختیاری `organizationUnitId`، `text`، `limit` (۱ تا ۳۰۰) و `page` برای صفحه‌بندی.
- صفحه جدید مستقل: `/organization/unit-locations-canonical` برای نمایش اطلاعات **ذخیره‌شده در همان جدول هدف** `ORG.ORGANIZATION_UNIT_LOCATIONS`، شامل آدرس، GEO، کدپستی، مختصات، دوره اعتبار و نسخه ردیف.
- جست‌وجو و صفحه‌بندی واقعی سمت سرور؛ کنترل زنده سازگاری با مبدأ: مقایسه ۱۹ فیلد محتوا و `LEGACY_POSTAL_ADDRESS_ID` با منابع قبلی، بدون تغییر مقادیر. وضعیت‌های `MATCH`، `DRIFT`، `NOT_BACKFILLED`، `MISSING_LOCATION`، `MISSING_ADDRESS` و `UNLINKED_ADDRESS` و `AMBIGUOUS_ADDRESS` گزارش می‌شوند.
- شمارش واحدهای دارای **بیش از یک مکان اصلی باز**؛ این کنترل **جایگزین بررسی هم‌پوشانی همه دوره‌های زمانی نیست**.
- API/نمای قدیمی R1 و فرم‌های قدیمی برای بررسی سازگاری حفظ شده‌اند؛ سورس R2-A فاقد DML/DDL است.

### هشدار همگام‌سازی

تا پیش از نصب قرارداد نوشتن یکپارچه، تغییر فرم‌های قدیمی `ORG.LOCATIONS`، `ORG.POSTAL_ADDRESSES` یا `ORG.ORGANIZATION_UNIT_LOCATIONS` ممکن است باعث اختلاف بین snapshot و داده مبدأ شود. نمایش `DRIFT`، حذف یا اصلاح خودکار ایجاد نمی‌کند. در زمان تست این مرحله، باید ورود/ویرایش داده‌های قدیمی متوقف یا کنترل شود.

### محدودیت‌های R2-A

- هنوز فرم نهایی ثبت/ویرایش تجمیعی (CRUD) فعال نیست.
- هنوز قواعد انتقال شعبه، تاریخچه، جلوگیری از بازه‌های هم‌پوشان و Audit با استفاده از تراکنش واحد پیاده نشده‌اند.
- هنوز قرارداد پشتیبانی از واحدهای مجازی/نشانی مرجع و نقاط خدمت مستقل نهایی نشده است.
- کدپستی همچنان اختیاری است؛ اختلاف رسمی شهرستان با GEO نباید به‌صورت خودکار «اصلاح» شود.
- هیچ جدول قدیمی و هیچ سطر واقعی حذف یا تغییر داده نشده است.

## ۳. مسیر تست


پس از Build در مرورگر صفحه `http://localhost:8091/#/organization/unit-locations-canonical` را باز کنید (به دلیل `withHashLocation()` وجود `#` الزامی است). انتظار بر پایه خروجی Oracle قبلی: تعداد کل ۱۳۴۰، منطبق ۱۳۴۰، انتقال‌نیافته ۰، اختلاف ۰، مراجع حذف‌شده ۰، نشانی چندگانه ۰ و مکان‌های اصلی باز تکراری ۰. اگر در این فاصله منابع قدیمی ویرایش شده باشند، اختلاف ممکن است واقعاً غیرصفر شود؛ آن را نباید پنهان کرد.

**پذیرش R2-A** مستلزم Build واقعی Angular + Backend، کنترل واقعی endpoint روی اتصال Oracle آزمایش و مشاهده صفحه در مرورگر است. آزمون‌های ایستا فقط قرارداد سورس را کنترل می‌کنند.

## ۴. کار بعدی — R2-B

1. تعیین مدل `LOCATION_USAGE_CODE` (فیزیکی، نشانی مرجع، و موارد استثنا) **در سطح استقرار**؛ مجازی‌بودن خود واحد باید جداگانه مدل شود.
2. طراحی رفتار ثبت جابه‌جایی: تاریخ شروع و پایان `[EFFECTIVE_FROM,EFFECTIVE_TO)`، رکورد جدید برای جابه‌جایی، ثبت دلیل/مصوبه و جلوگیری از بازه‌های هم‌پوشان با تراکنش/قفل معتبر.
3. طراحی سازگاری با نقاط خدمت مستقل و مکان‌های مشترک؛ بدون حذف `LOCATIONS` تا قطع وابستگی‌ها.
4. انتخابگر معتبر GEO، اختیاری‌بودن کدپستی و مختصات، محافظت از اطلاعات رسمی شعب بانک ملت، کنترل نسخه و Audit.
5. پس از UAT، کنارگذاری فرم‌های موازی با استراتژی Cutover دوطرفه یا قفل نوشتن از منبع قدیمی و کنترل Drift؛ حذف جدول آخرین اقدام است.
