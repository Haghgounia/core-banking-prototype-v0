# DPS2 0.11.0 / Phase 11F — PDL Term Configuration Reconciliation

## Problem confirmed at runtime

Phase 11F Runtime E2E rejected legacy term-family accounts 6 and 7 because no operational `DEPOSIT_TERM_CONTRACT` existed. The bootstrap then inspected Product Versions 3 and 4 and the full PDL catalog. Both versions were opening-eligible term products but neither had an active `DEPOSIT_PRODUCT_TERM_RULE`; therefore no governed `DEPOSIT_PRODUCT_ALLOWED_TERM` could be resolved.

Observed terminal condition:

`NO_OPEN_TERM_PRODUCT_VERSION_WITH_GOVERNED_ALLOWED_TERM`

This is a Product Definition Layer data/configuration gap, not a defect in the Phase 11F term-operation service.

## Reconciliation strategy

A metadata-driven, idempotent repair utility is added:

`tools/reconcile-pdl-term-config-phase11f.mjs`

The utility uses the public Product Builder API and the live Oracle descriptors instead of hard-coding an assumed physical schema. It:

1. Finds `DEPOSIT` products in `SHORT_TERM_DEPOSIT` / `LONG_TERM_DEPOSIT`.
2. Selects Product Versions that are `ACTIVE` or `APPROVED`, have `ORIGINATION_STATUS_CODE=OPEN`, active record status, and current date validity.
3. Detects existing active `DEPOSIT_PRODUCT_TERM_RULE` rows.
4. Creates a missing Term Rule only when necessary.
5. Detects a usable active `DEPOSIT_PRODUCT_ALLOWED_TERM` child.
6. Resolves `MATURITY_ACTION_CODE` from governed maturity-action reference data (`dps2-maturity-action`) and prefers business-valid actions such as `RENEW_PRINCIPAL`; it never uses lifecycle status values such as `ACTIVE` as a maturity action.
7. Creates a missing allowed term using a version-scoped Phase 11F fixture code (for example `P11F_4_30D`) with a canonical duration candidate (`30 / DAY`) only as a controlled reconciliation fixture for the prototype catalog.
8. Treats `DATA_CONFLICT` from Oracle Check Constraints as a rejected candidate and tries the next governed maturity-action / term-unit candidate without leaving a partial row.
9. Re-reads PDL and verifies that at least one opening-eligible term Product Version now exposes a usable governed allowed term.

The tool supports `DRY_RUN` by default. Mutation occurs only with `--apply`.

## Runtime conflict found and corrected

The first APPLY attempt failed with `DATA_CONFLICT` while inserting `DEPOSIT_PRODUCT_TERM_RULE`. The rejected payload contained `MATURITY_ACTION_CODE=ACTIVE`. That value was generated by the generic fallback because the column name ends in `_CODE`, but it is semantically invalid: `MATURITY_ACTION_CODE` describes the maturity behavior, not record status.

The same run exposed a metadata parsing defect: a compound Oracle Check Constraint such as `IS_RENEWABLE IN (0,1) AND IS_ACTIVE IN (0,1)` was being parsed as one greedy `IN` expression, producing a malformed descriptor option similar to `1) AND IS_ACTIVE IN (0,1`. `PdlProductBuilderRepository` now scans all independent `IN (...)` clauses inside a compound constraint. The reconciliation script also filters malformed legacy descriptor options so the currently running 0.11.0 JAR does not need to be restarted for this repair.

## Architectural note

Normal product lifecycle must configure TERM rules while the Product Version is in its governed configuration lifecycle. This repair exists only to reconcile prototype Product Versions created before the TERM readiness contract was enforced. It must not become the normal Product Factory publication path.
