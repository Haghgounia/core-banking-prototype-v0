# چک‌لیست نهایی‌سازی محصول‌ساز مشترک — RC1

راهنما: `✅` فقط با سند/لاگ و امضای صاحب کنترل. وضعیت اولیه موارد انجام‌نشده `☐` است. **موفقیت Build / وجود جدول / امکان ذخیره Draft معادل مصوبه بانکی نیست.**

## A — مبنای نسخه و Build

- ☐ منبع ZIP دقیق 0914 با SHA-256 ثبت شده و عدم نیاز به اجرای مجدد Patch قدیمی HF9-HF1 تأیید شده است.
- ☐ Full Windows Maven + Angular: BUILD SUCCESS، صفر Fail/Error، Skipped بررسی شده است.
- ☐ آزمون‌های مثبت و منفی Ruleهای سپرده و تسهیلات در Maven واقعی اجرا شده‌اند.
- ☐ اسکریپت‌های رگرسیون فعلی HF7/HF8/HF9 همگی موفق‌اند؛ کنترل قدیمی منسوخ جدا گزارش شده است.
- ☐ فایل‌های FEE، FEE2، Posting و سایر زیرسامانه‌ها از تغییرات ناخواسته محفوظ مانده‌اند.

## B — مدل داده / Oracle

- ☐ **۵۴ جدول** PDL روی Oracle هدف موجود و با رجیستر تطبیق دارند.
- ☐ انواع، طول، precision، scale، nullable و مقادیر پیش‌فرض بر اساس مستند مرجع بررسی شده‌اند.
- ☐ PK/FK/UK/CHECK و وضعیت ENABLED/VALIDATED بررسی شده‌اند.
- ☐ قرارداد منحصر‌به‌فردی `PRODUCT_RATE_TIER` و رابطه والد/فرزند با فیزیک Oracle مقایسه شده است.
- ☐ تفاوت **۴۷ جدول / ۶۶۱ فیلد مدل مرجع** با ۵۴ جدول فیزیکی شناخته شده تحلیل شده است؛ بدون هم‌ارز انگاشتن آنها.
- ☐ رکوردهای Legacy/Deprecated و ارجاعات شکسته فقط خواندنی ارزیابی شده‌اند؛ پاک‌سازی خودکار انجام نشده است.

## C — هویت، نسخه و حاکمیت

- ☐ کد محصول فقط پس از مسیر صدور سیستمی ایجاد شده و تغییرناپذیری هویت احراز شده است.
- ☐ خانواده تسهیلات از LOAN_TYPE فعال و گروه عقد و خانواده سپرده از کدهای معتبر مشتق شده‌اند.
- ☐ ماژول غیرفعال سوابق را حفظ می‌کند و نبود Rule غیرفعال موجب الزام کاذب نیست.
- ☐ کل محدوده تاریخ اعتبار، همپوشانی، Gap، وضعیت فعال/غیرفعال، تعارض و Child FK کنترل شده‌اند.
- ☐ ثبت/ویرایش/تصویب با کنترل Backend همسازند و API قابل دورزدن نیست.
- ☐ `canApprove` از `canOpen` مستقل است؛ تمام خانواده‌های آزمون `canOpen=false` را حفظ می‌کنند.

## D — قواعد مشترک

- ☐ اهلیت و معیار فرزند با نوع مشتری، جنسیت، مدارک و استعلام سازگارند.
- ☐ کانال والد و Operation فرزند تناقض بدون مجوز تولید نمی‌کنند.
- ☐ محدوده سازمانی و ارز، نسخه و اولویت Scope موردنظر بانک را رعایت می‌کنند.
- ☐ مدارک و استعلام‌های اجباری و وابستگی به مرحله چرخه‌عمر بررسی شده‌اند.
- ☐ سه‌سطح قیمت‌گذاری Rule → Component → Tier با FK و تاریخ صحیح کار می‌کند.
- ☐ قرارداد مبلغی HF9: نرخ منتخب روی کل مبلغ، `[Min,Max)` و `NULL` نامحدود، بدون Gap/Overlap رعایت شده است.
- ☐ پله مدت‌دار بدون قرارداد مرز/واحد/دامنه، به‌اشتباه مجوز تصویب نمی‌گیرد.
- ☐ رابطه بین محصولات با مالکیت نسخه مقصد، عدم خودارجاع و عدم تکرار مؤثر کنترل می‌شود.

## E — محصولات سپرده

- ☐ هر ۷ خانواده سپرده (از جمله نوسترو/وسترو) Applicability مناسب دارند.
- ☐ افتتاح، حداقل/حداکثر مبلغ، Overdraft، معرفی‌کننده و شرایط وابسته معتبرند.
- ☐ نوع تراکنش و `IS_ALLOWED` به تنهایی مجوز عملیاتی محسوب نشده؛ الزام سایر شروط به تأیید کارشناس رسیده است.
- ☐ ابزار برداشت، نوع سپرده و عملیات کانال سازگارند.
- ☐ حساب مشترک، تعداد مالک، قواعد امضا و صاحبان امضا سازگارند.
- ☐ راکدی/بازفعال‌سازی و مسدودی‌های متعدد، رفتار روشن و مصوب دارند.
- ☐ مدت، مدت‌های مجاز، حالت پیش‌فرض، سررسید و تمدید تأیید شده‌اند.
- ☐ سود: برنامه، تناوب، روز پرداخت، تعدیل تعطیل، مقصد و سرمایه‌سازی، هم در ثبت و هم تصویب معتبرند.
- ☐ خاتمه: Precheck/Settlement/Approval، ترتیب و مقصد، و آثار مانده/مسدودی بررسی شده است.
- ☐ نوسترو/وسترو: Profile و Settlement جداگانه، و بدون مجوز افتتاح عملیاتی ارزیابی شده‌اند.

## F — محصولات تسهیلات

- ☐ Loan Type / Plan Type / Currency / Group با مراجع معتبر و فعال همخوانی دارند.
- ☐ وابستگی Loan Usage، زیربخش اقتصادی، پارامتر عملیاتی و رابطه زیر‌بخش/طرح در مسیر ثبت **و تصویب** تعیین تکلیف شده است.
- ☐ سهم مشتری فقط برای مشارکت مدنی و به‌صورت درصدی با نسبت ذخیره‌سازی صحیح کنترل می‌شود.
- ☐ قواعد بازپرداخت، دوره تنفس، پیش‌پرداخت، وثیقه، ریسک و گردش کار به تفکیک عقد تأیید شده‌اند.
- ☐ افزونه اهلیت تسهیلات فقط فرزند اهلیت مشترک است، نه Rule تکراری.
- ☐ مراحل Origination/Disbursement/Repayment/Collection تا احراز مستقل Runtime باز نشده‌اند.

## G — تجربه کاربری و Feedback

- ☐ هر فرم: نمایش فیلد، نوع کنترل، کد مرجع فارسی/لاتین، مقدار پیش‌فرض، اجباری بودن و پیام خطا بازبینی شده است.
- ☐ ذخیره → بازخوانی → ویرایش → بازخوانی مستقل برای هر بخش موفق است.
- ☐ گرید، تعداد رکورد، فیلتر، صفحه‌بندی، فرزند، اندازه تاریخ و Layout RTL صحیح‌اند.
- ☐ هر شکست دارای شناسه سناریو، شرح گام‌ها، نتیجه واقعی و تصویر/لاگ پیوست است.
- ☐ موضوع نیازمند تصمیم کسب‌وکاری از Defect پیاده‌سازی تفکیک شده است.

## H — مجوز تحویل و نهایی‌سازی

- ☐ گزارش Windows Build و Oracle Read-only در مخزن شواهد موجود است.
- ☐ Defect با شدت بحرانی/بالا برای Scope مورد پذیرش باز نمانده یا با مصوبه صریح از Scope کنار گذاشته شده است.
- ☐ مالک سپرده، تسهیلات، بین‌الملل، ریسک، انطباق، معماری داده، QA و مدیر انتشار نظرشان را امضا کرده‌اند.
- ☐ برچسب این مرحله **Business UAT RC** است و هرگونه مجوز Production جداگانه صادر می‌شود.
