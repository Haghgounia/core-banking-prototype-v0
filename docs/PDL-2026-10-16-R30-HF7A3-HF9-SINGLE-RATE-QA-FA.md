# PDL R30-HF7A3 / HF9 — گزارش پیاده‌سازی Final-C2

**تاریخ:** ۲۰۲۶-۱۰-۱۶  
**Baseline الزامی:** R30-HF7A3-HF8؛ در محیط کاربر Build موفق با ۲۲۲ آزمون JUnit، صفر Failure و Error و یک Skipped  
**نوع تحویل:** Patch محدود سورس/Backend، بدون DDL/DML و بدون تغییر FEE، FEE2 یا موتورهای عملیاتی DPS2.

## ۱. تصمیم‌های مصوب و رفتار پیاده‌سازی

1. سیاست محاسبه `SINGLE_APPLICABLE_RATE`: یک نرخ پله برای **کل مبلغ مبنای همان مؤلفه**؛ نه مدل تجمیع تصاعدی (Marginal).
2. مبلغ هر پله `[MIN_AMOUNT, MAX_AMOUNT)`؛ حداقل شامل و حداکثر غیرشامل است. مقدار `MAX_AMOUNT == MIN_AMOUNT` یک بازه تهی و غیرقابل تصویب/ثبت است.
3. `MIN_AMOUNT=NULL` یعنی نبود حد پایین و `MAX_AMOUNT=NULL` یعنی نبود حد بالا در همان سمت. **NULL به صفر تبدیل نمی‌شود.** برای اثبات پوشش، حدود مؤلفه `PRODUCT_PRICING_COMPONENT` نیز دقیقاً به همین شکل تفسیر می‌شوند.
4. ممیزی هر مؤلفه فعال، در تمامی تغییرات مؤثر زمانی خودش مستقل انجام می‌شود. اتحاد پوشش زمانی چند مؤلفه جانشین پوشش هیچ مؤلفه‌ای نیست. برای هر مبلغ در دامنه مؤلفه، در هر روز مؤثر، دقیقاً یک پله نرخ معتبر لازم است.
5. گسست مبلغ، هم‌پوشانی مبلغ، پله خارج از دامنه مؤلفه، پله با نرخ نامعتبر، FK غلط، تاریخ نامعتبر، وضعیت ناشناخته و بازیابی ناقص فرزند، مانع طراحی قابل تصویب می‌شوند.
6. `PRICING_METHOD_CODE=TIERED` باید با `IS_TIERED_RATE=1` سازگار باشد. این کنترل در گزارش تصویب انجام می‌شود؛ حالت Draft سابق بدون اصلاح خودکار باقی می‌ماند.
7. برای کران‌های **مدت** هیچ فرضی دربارهٔ شمول دو طرف، تبدیل ماه به روز، یا تبدیل واحدهای مرجع عددی DPS انجام نمی‌شود. اگر فقط یکی از `MIN_TERM_VALUE/MAX_TERM_VALUE` موجود باشد، وضعیت `INVALID_SEMANTICS` است. اگر هر دو کران مدت موجود باشند، تا تصویب **دامنه مجاز مدت و شمول مرزهای مدت**، کل مؤلفه وابسته به مدت در Gate تصویب Fail-Closed می‌شود. هر دو NULL همراه با `TERM_UNIT_CODE=NULL` همان «پله فقط مبلغی» موجود است. این یک **محدودیت موقت آگاهانه** است، نه ادعای تکمیل موتور انتخاب مدت.
8. تابع `previewAmountOnlyRate` فقط بازبینی طراحی و اثبات انتخاب نرخ است؛ **نه محاسبه سود، نه فراخوانی Runtime و نه Posting**. هیچ اتصالی برای `canOpen=true` ایجاد نشده است.

## ۲. فایل‌های عملیاتی مرتبط

- جدید: `ProductPricingSingleRatePolicy.java` — انتخاب آزمایشی مبلغ و اثبات تقسیم‌بندی/مرزبندی پله، بدون write.
- اصلاح: `ProductRuleHierarchyAudit.java` — ممیزی هر مؤلفه/روز با FK، اعتبارسنجی داده و Fail-Closed.
- اصلاح: `ProductRuleSemanticContract.java` — اعتبارسنجی `[Min,Max)` برای پله و مؤلفه در ورودی CRUD و ممیزی.
- جدید: `ProductRateTierHF7A3HF9Test.java` (۲۹ سناریو)، `ProductPricingPublicationHF7A3HF9Test.java` (۷ سناریوی جدید JUnit برای report و transition).
- جدید: `tools/verify-pdl-r30-hf7a3-hf9-single-rate.mjs`.
- اصلاح محدود Harnessهای گذشته برای وابستگی کلاس جدید و همخوانی Fixture پله‌ای؛ **آزمون‌های منفی قبلی حذف نشده‌اند**.
- `build-production.cmd` و `build-production.sh`: اجرای Validator جدید قبل از Build اصلی.

### ریسک‌های باقیمانده که عمداً حل نشده‌اند

- **مدت:** بدون سیاست مصوب تعیین دامنه و شمول مرزهای مدت، حتی پله مدت‌دار با حداقل و حداکثر مشخص نیز قابل تصویب نیست. این وضعیت در پیام Governance توضیح داده می‌شود.
- **دامنه مبلغ در سطح محصول:** فقط بازه مستند در همان مؤلفه اثبات می‌شود؛ حدود مستقل نوع محصول یا Runtime از NULL یا داده نمونه استنتاج نمی‌شوند.
- **یکتایی فیزیکی `(PRICING_COMPONENT_ID,TIER_NO)`** هنوز با `ALL_CONSTRAINTS` Oracle واقعی تطبیق نشده است؛ همان قرارداد تاریخی تکرار شماره پله در روزهای جدا برای جلوگیری از تغییر بدون سند حفظ شد.
- **روش/هدف/مبنای درصد و Snapshot عملیاتی:** این Patch موتور واقعی قیمت‌گذاری سود سپرده، تسهیلات یا کارمزد نیست و تغییری به FEE یا FEE2 نمی‌دهد.
- **امنیت وابستگی‌های Frontend:** هشدارهای پیشین `npm audit` باید مستقل بررسی شوند و از این Patch رفع نشده‌اند.

## ۴. نصب امن و پذیرش HF9 در ویندوز

قبل از هر کار نسخه پشتیبان HF8 را نگه دارید. **Patch صرفاً روی HF8 موفق و بدون تغییرات محلی متعارض نصب شود.** ZIP Patch با ساختار نسبی ریشه پروژه تهیه شده و نیاز به DDL، مهاجرت Oracle یا Seed ندارد.

```bat
cd /d D:\Projects\core-banking-prototype-v0
node tools\verify-pdl-r30-hf7a3-hf9-single-rate.mjs
node tools\verify-pdl-r30-hf7a3-hf8-final.mjs
node tools\verify-release-layout.mjs
build-production.cmd > "%TEMP%\HF9-build.log" 2>&1
```

پس از اجرا لاگ `%TEMP%\HF9-build.log` برای تأیید تعداد JUnitها، نتیجه نهایی Build و خطاهای احتمالی لازم است. **وجود PASS در آزمون ایستا به معنی تأیید واقعی Oracle یا افتتاح حساب نیست.**

## ۵. معیار پذیرش

- مورد مثبت: برای یک مؤلفه با دامنه معلوم و بازه‌های مبلغ مجاور، `canApprove=true` در طراحی معتبر و `canOpen=false` تا مدارک مستقل Runtime.
- موارد منفی: هر هم‌پوشانی/گسست مبلغ، نقص زمانی هر مؤلفه، FK نامعتبر، روش ناسازگار و عدم قطعیت مدت باید در `effectiveRules` با دلیل و `canApprove=false` نمایان شوند.
- بدون تغییر در `VERSION`، Oracle، FEE/FEE2، Angular، DPS2، عملیات حساب یا حسابداری.
- پذیرش نهایی HF9 پس از Build کامل Maven+Angular در سیستم کاربر.
